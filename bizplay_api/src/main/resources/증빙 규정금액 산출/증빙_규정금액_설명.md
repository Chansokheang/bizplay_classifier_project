## §0 요약 — 무엇이 빠져 있는가

### 0-1. 규정금액은 API 응답이 아니라 계산 결과다

규정금액이 증빙에 실리기까지는 3층이다.

| 층 | 하는 일 | 주체 |
|---|---|---|
| ① 원자료 조회 | 용도·급지·기간별 **기준금액**을 받는다 | 백엔드 `POST /api/v2/bstr/policy/renewal/limit` |
| ② 조건식 적용 | 응답의 `appliedConditions[]` 를 **일자별로 적용**해 최종 규정금액을 만든다 | **호출하는 쪽(클라이언트)** |
| ③ 검증 | 초과금액 산출 · 신청금액 상한 · 상신 차단 | 호출하는 쪽 |

**②가 클라이언트 몫이다.** 백엔드는 조건 **매칭 결과**(어떤 조건이 걸리는가)만 판정해 내려주고, 그 조건을 금액에 적용하는 산술은 하지 않는다.

```java
// BstrRenewalLimitService.java:149
baseResult.setAppliedConditions(appliedConditions);
baseResult.setDayTypeMap(dayTypeMap);
// limitAmounts는 기준금액 그대로 유지 (프론트가 조건 적용하여 최종 금액 산출)
```

같은 파일 `buildAppliedConditions` 블록 주석이 배경을 밝힌다.

> 기존에는 백엔드가 직접 금액을 계산했으나, 이제 조건식 정보만 프론트에 전달하여 프론트가 기준금액에 sortOrder 순서로 조건을 적용하여 최종 금액을 산출한다.

### 0-2. ⚠️ 저희 Swagger 설명문이 구현과 반대로 적혀 있습니다

```
BstrPolicyRenewalController.java:42-43   "가감이 적용된 최종금액을 반환한다"   ← Swagger 설명 (틀림)
BstrRenewalLimitService.java:149          limitAmounts 는 기준금액 그대로 유지  ← 실제 구현
```

**API 문서만 보고 조립하면 반드시 틀립니다.** `limitAmounts` 를 최종 규정금액으로 읽고 계셨다면 원인은 이 설명문입니다. 컨트롤러 설명문은 별건으로 정정하겠습니다.

### 0-3. 현재 상태 진단 — 검증이 없는 것이 아니라 항상 통과한다

`260819 문의/requestBody_settlement_fixed.json` 실측입니다.

| 경로 | 값 |
|---|---:|
| `bstrReceipts[0].tranKindType` | `"TRANSPORT"` |
| `bstrReceipts[0].approvalAmount` | 15,000 |
| `bstrReceipts[0].ruledAmount` | **15,000** ← 승인금액과 동일 |
| `bstrReceipts[0].bstrPayClassType` | **null** |
| `bstrReceipts[0].excessReason` | `""` |

초과금액 공식이 `MAX(0, 사용금액 − 규정금액)` 이므로 `MAX(0, 15,000 − 15,000) = 0` 입니다.

**규정금액을 승인금액으로 채우면 초과금액이 구조적으로 항상 0** 이 됩니다. 규정금액 검증이 "동작하지 않는" 것이 아니라, **항상 통과하도록 값이 들어가 있는** 상태입니다.

다만 무력화되는 범위는 검증마다 다릅니다 — **판정축이 하나가 아닙니다**(§1-3).

| 검증 | 축 | `ruledAmount = approvalAmount` 일 때 |
|---|---|---|
| **⑰** 초과금액 분할 미처리 | 사용금액 | **발동하지 않는다** — 초과금액이 항상 0 |
| **⑫** 초과사유 미입력 (단건 비교 분기) | 신청금액 | **발동하지 않는다** — 신청금액 ≤ 승인금액 = 규정금액 |
| **⑫** 초과사유 (식비 일별 합산 · 전체기간 `ALL`) | 신청금액 **합산** | **발동할 수 있다** — 합산이 한도를 넘을 수 있고, `ALL` 은 한도를 서버에서 다시 조회하므로 증빙의 `ruledAmount` 와 무관하다 |
| **⑪** 숙박비 / 식비 총액 초과 | 신청금액 **합산** | **발동할 수 있다** — 같은 이유 |

즉 "전부 통과"가 아니라 **단건 판정만 무력화**되고 합산 판정은 남습니다. 그래서 증상이 "검증이 아예 없다"가 아니라 "될 때도 있고 안 될 때도 있다"로 보일 수 있습니다.

`bstrPayClassType`(지급구분)이 `null` 인 것은 별개의 공백입니다. 이 값이 없으면 신청금액 상한 판정이 `default` 분기로 흘러 **지급구분이 의도한 상한이 적용되지 않습니다.**

| 지급구분 | 의도한 상한 | `null` 일 때 실제 |
|---|---|---|
| `FIXED` | `ruledAmount` | `default` 분기 |
| `LIMITED` | `MIN(ruledAmount, approvalAmount)` | `default` 분기 |
| `FUEL` | `ruledAmount` | `default` 분기 |

`default` 분기의 결과는 카드유형에 따라 갈립니다 — 기타증빙(`ETC`)은 `MIN(규정, 승인)`, 카드 매입내역(비 `ETC`)은 **무제한**입니다.

> 참고로 위 260819 증빙은 `bstrReceiptType = "ETC"` 이므로 상한이 `MIN(15,000, 15,000) = 15,000` 이 되어 **상한 위반은 아닙니다.** 이 증빙에서 실제로 문제인 것은 규정금액 하나입니다. 다만 지급구분이 `FIXED`·`LIMITED` 인 용도에서 이 값을 비우면 상한이 규정금액과 무관해지므로, 규정금액과 **한 쌍**으로 채우시는 것이 안전합니다.

### 0-4. 저희가 드린 샘플에 이 공백이 있었습니다 — 정정합니다

`정산서-공유자료/정산서_requestBody_샘플.json` (원본은 이미 배포됐으므로 고치지 않고 여기서 정정합니다)

| 위치 | 필드 | 배포된 값 | 정정 |
|---|---|---:|---|
| `bstrReceipts[0]` (TRANSPORT) | `ruledAmount` | **0** | 한도 조회 → 조건식 적용 결과를 넣습니다. 교통비 등급제(`bstrCategoryType='GRADE'`)라면 `approvalAmount` 가 맞습니다 → `04_용도별_산출경로.md` §4.4 |
| `bstrReceipts[0]` | `bstrPayClassType` | **null** | 한도 응답의 `bstrPayClassType` 을 그대로 넣습니다 (`FIXED`·`ACTUAL`·`ACTUAL_FIXED`·`LIMITED`·`FUEL`·`TOLL`·`NONE`) |
| `bstrReceipts[1]` (FOOD) | `bstrPayClassType` | **null** | 위와 동일 |
| `bstrReceipts[*]` | `approvalTime` | `"081500"` / `"123200"` | `"08:15:00"` / `"12:32:00"` — `LocalTime` 이므로 `HH:mm:ss` (260810 답변서 §5-1 에서 이미 정정. 수정본에 반영된 것을 확인했습니다) |

참고로 같은 샘플의 자동증빙(`etcReceiptSaveRequests[0]`, 일비)은 `ruledAmount = 60,000` · `bstrPayClassType = "FIXED"` 로 **올바르게** 채워져 있습니다. 자동증빙과 수동 증빙의 이 차이가 혼란의 원인이었을 수 있습니다.

### 0-5. 그래서 무엇을 하면 되는가

1. **①을 호출한다** — `POST /api/v2/bstr/policy/renewal/limit`. 요청 필드와 `calcInputs` 채우는 법은 `01_원자료조회_계약.md`.
   - 급지가 여러 개거나 식비에 동행인이 있으면 **조합마다 나눠 호출**해야 합니다 → `04_용도별_산출경로.md` §4.10
2. **②를 구현한다** — 응답의 `appliedConditions[]` 를 `sortOrder` 순서로 일자별 적용. 규칙은 `02_조건식적용_규칙.md`, 검산은 `03_검산예시.md`.
3. **증빙 필드에 넣는다** — §1 필드 맵.
4. **②를 골든 벡터로 검증한다** — `규정금액_골든벡터.json` 의 71건을 자기 구현에 넣고 `expected.limitAmounts` 와 대조합니다. **문서를 읽고 구현한 뒤 반드시 이 단계를 거치십시오** — 규칙을 문장으로 이해해도 구현이 어긋나는 지점이 여럿 있습니다(아래 참고).
5. **③을 돌린다** — `06_검증.md` §6.6 체크리스트.

> **골든 벡터가 잡아내는 것** — 저희가 이 벡터를 만들면서도 두 군데를 틀렸습니다.
> ① `fixed`·`silbiLimit` 는 `operatorValue` 가 아니라 **`fixedAmount`** 를 쓰고, 그 값이 `null` 이면
> 금액을 **그대로 둡니다**(0 이 아닙니다 — 벡터 `B-09b`).
> ② `silbiLimit` 은 `min` 이 아니라 **대체**라서 한도가 기준금액보다 크면 금액이 올라갑니다(`B-11b`).
> 규칙은 `02_조건식적용_규칙.md` 에 정확히 적혀 있었는데도 구현에서 어긋났습니다. 벡터로 대조하면 바로 드러납니다.

## §1 규정금액이 실리는 필드

규정금액이 관여하는 배열은 셋이고, **형태가 서로 다릅니다.**

| 배열 | 성격 | 규정금액 계열 필드 |
|---|---|---|
| `issuedFields[].issuedReceiptDtos[]` | 수동 증빙(발행영수증) 연결분 | `ruledAmount` · `overseasRuledAmount` · `reqAmt` |
| `etcReceiptSaveRequests[]` | 자동증빙 (문서와 **함께** 생성) | `ruledAmount` · `reqAmt` · `bstrPayClassType` |
| `bstrReceipts[]` | 전표 라인용 스냅샷 (**PK 있는 증빙만**) | `ruledAmount` · `overseasRuledAmount` · `excessReason` · `reqAmt` · `bstrPayClassType` |

`bstrReceipts[]` 원소는 **58필드를 평면**으로 갖고(`slipAmt`·`accountSubject*`·`budgetDepartment*`·`taxCode*`), 나머지 둘은 같은 정보를 **중첩 `slip` 객체**로 갖습니다. 한쪽 형태를 다른 쪽에 쓰면 안 됩니다.

| `slip` 객체 | 저희 클라이언트가 보내는 키 수 | 차이 |
|---|---:|---|
| `issuedFields[].issuedReceiptDtos[].slip` | 19 | `docDate`(전기일)를 함께 보낸다 |
| `etcReceiptSaveRequests[].slip` | 18 | `docDate` 를 보내지 않는다 |

> 이것은 **저희 송신분의 비대칭이지 DTO 제약이 아닙니다** — 백엔드는 양쪽 모두 같은 `SlipDto` 를 쓰고 `docDate` 도 그 안에 있습니다. 자동증빙에 `docDate` 를 넣어도 400 이 되지는 않습니다.

### 1-1. 필드별 의미

| 필드 | 통화 | 무엇을 넣는가 |
|---|---|---|
| `ruledAmount` | **원화** | ②의 최종 산출값. 외화 규정이면 환산한 원화. 초과 판정·신청금액 상한의 기준 |
| `overseasRuledAmount` | 외화 원금 | 외화 규정의 원 통화 금액. **초과 판정에는 쓰지 않습니다** — 규정금액 컬럼 표기와 외화 비교 cap 용도 |
| `reqAmt` | 원화 | 신청금액. 상한이 지급구분별로 다릅니다 → `06_검증.md` §6.3 |
| `excessReason` | — | 초과사유. 관리자가 그 용도에 설정을 켜 두고 ⑫ 판정(**신청금액 축** — §1-3)이 초과면 필수. 초과금액 컬럼(사용금액 축)과 판정이 갈릴 수 있습니다 |
| `bstrPayClassType` | — | 지급구분. 한도 응답 값을 그대로. **비우면 지급구분별 상한(`FIXED`→규정금액 등)이 적용되지 않고 `default` 분기로 흐릅니다** |
| `dividedRuledAmount` | 원화 | 비율분할(IO/WBS) 자식 행의 자기 몫 규정금액. **전송하지 않습니다**(`prepare-save-data.ts` 에 없음). 다만 표시 전용은 아니고 **초과 판정**(`over-amount.ts:145-150`)·**신청금액 cap**(`autofill-req-amount.ts:145-151`)·위반의심 ⑧ 이 이 값을 씁니다 |
| `divisionOrder` | — | 분할 순번. 비분할이면 `null`. **항상 함께 보내야 합니다** — 빠뜨리면 백엔드가 부모 `receiptId` 단위 「첫 non-null」 규칙으로 폴백해 **첫 행의 사유가 나머지 행을 덮습니다**(초과분 행에 지울 수 없는 사유가 남던 원인) (`prepare-save-data.ts:218-221`) |
| `complianceTypesStr` | — | 위반의심 태그(쉼표 구분). **저희 화면이 계산해 저장하는 파생 필드**입니다 — 직접 조립하면 붙지 않거나 잘못 붙습니다. 상신은 막히지 않지만 관리자 판독이 달라집니다 → 아래 1-4 |

### 1-2. ⚠️ 저장 시 `null` 이 `0` 으로 바뀝니다

```ts
// prepare-save-data.ts:204-205
ruledAmount: r.ruledAmount ?? 0,
overseasRuledAmount: r.overseasRuledAmount ?? 0,
```

화면 판정에서는 규정금액 `null`(= 규정 미조회 → **초과 판정 안 함**)과 `0`(= 한도 0원 → **전액 초과**)이 다르게 취급되지만, 저장 payload 에서는 `null` 이 `0` 으로 강제됩니다. 즉 **규정을 조회하지 못한 증빙과 한도가 0원인 증빙이 저장 후 구별되지 않습니다.**

실무상 의미는 이렇습니다.

- 규정을 조회할 수 없는 용도라면 `0` 을 넣는 것이 현행 동작과 같습니다.
- 다만 `0` 은 초과 판정 대상이므로, 사용금액 전액이 초과금액이 되어 ⑫초과사유가 요구될 수 있습니다.
- `excessReason` 도 `?? ''` 로 빈 문자열이 되므로(`:224`), 초과가 있는데 사유가 없으면 상신이 막힙니다.

### 1-3. ★ 판정축이 하나가 아닙니다 — 사용금액 축과 신청금액 축이 공존합니다

**"규정금액을 무엇과 비교하는가"가 용도에 따라 다릅니다.** 하나로 통일해 구현하면 우리 화면과 다른 판정이 나옵니다.

| 대상 | 비교 대상 | 외화 처리 | 정본 |
|---|---|---|---|
| 초과금액(본인부담) 컬럼 · **⑰** 초과분할 미처리 차단 | **사용금액** (`approvalAmount`, 일비는 `supplyAmount+vatAmount`) | **원화 환산끼리** | `over-amount.ts` |
| **⑪** 숙박비/식비 총액 초과 · **⑫** 초과사유 필수 · 화면 일별 초과 판정 | **신청금액** (`reqAmt`) | **외화 원금끼리** (`foreignAmount` vs `overseasRuledAmount`) | `validate-total-exceed.ts` · `validate-excess-reason.ts` · `exceed-check-utils.ts` |

- **왜 다른가** — 초과금액(본인부담)은 *실제로 얼마를 썼는지*에서 나오는 회계 금액이라 사용금액 축입니다. 반면 ⑪·⑫는 *얼마를 청구했는지*를 규정 한도와 견주는 것이라 신청금액 축입니다.
- **실무상 결과** — 신청금액이 규정금액까지만 자동 채워진 증빙은 **초과금액 컬럼에는 초과가 보이는데 ⑪·⑫는 통과**합니다. 반대로 사용금액이 규정 이내인데 신청금액을 임의로 크게 넣으면 ⑪·⑫만 막습니다.
- **외화가 특히 갈립니다** — 초과금액 컬럼은 원화 환산 금액끼리 비교하고, ⑪·⑫는 외화 원금끼리 비교합니다. 같은 증빙에서 한쪽은 초과, 다른 쪽은 이내가 될 수 있습니다.

⑫의 세부 분기(`ACTUAL` / `ONE_DAY` 비식비 / `ONE_DAY` 식비 합산 / `ALL` 전체기간)는 `06_검증.md` §6.5.7 에 판정식과 함께 있습니다.

**두 축의 소비처 전수**

| 축 | 소비처 |
|---|---|
| 사용금액 | 초과금액 컬럼 · ⑰ 초과분할 차단 · **위반의심 ⑧ 법인카드초과**(`compliance-attach.ts:226`) · **초과금액 분할 payload**(`build-excess-split-payload.ts:121`) · `merge-divided-receipt.ts:190` — 뒤 세 곳도 `getExcessJudgmentAmount` 를 씁니다 |
| 신청금액 | ⑪ 총액 초과 · ⑫ 초과사유 · 화면 일별 판정 · **위반의심 ⑦ 규정초과**(`compliance-attach.ts:215`) |

### 1-4. 위반의심 태그(`complianceTypesStr`)도 규정금액으로 계산됩니다

저희 화면이 계산해 저장하는 **파생 필드**입니다. requestBody 를 직접 조립하면 이 태그가 붙지
않거나 잘못 붙습니다 — **상신은 막히지 않지만 관리자 판독 결과가 달라집니다.**

| 태그 | 판정식 | 축 | 설정 게이트 |
|---|---|---|---|
| `RULED_AMOUNT_EXCEED` (⑦ 규정초과) | `ruledAmount != null ∧ (reqAmt ?? 0) > ruledAmount` | **신청금액** | **없음 — 무조건 부착** |
| `CORP_CARD_LIMIT_OVER` (⑧ 법인카드초과) | `getExcessJudgmentAmount(r) > (dividedRuledAmount ?? ruledAmount)` ∧ `cardType === 'CORP'` | **사용금액** | `bstrCorpCardLimitOverUsed` |

- 초과금액 분할된 증빙(`isExcessSplitReceipt`)은 두 태그의 **판정 대상에서 빠집니다** — 그래야 "초과금액은 0인데 비고엔 규정초과"가 뜨지 않습니다.
- **여기서도 축이 갈립니다** — ⑦은 신청금액, ⑧은 사용금액입니다(§1-3 의 세 번째 사례).
- 태그는 쉼표로 이어 붙입니다. 미해당이면 빈 문자열입니다.
- 상세는 `06_검증.md` 부록 A-0.

## §7 자주 나오는 오해

| # | 오해 | 실제 |
|---|---|---|
| 1 | 응답 `limitAmounts` 가 최종 규정금액이다 | **기준금액**입니다. 조건식을 적용해야 최종금액이 됩니다. Swagger 설명문이 반대로 적혀 있습니다(§0-2) |
| 2 | 규정금액을 승인금액으로 채우면 된다 | 아무 증빙에나 그렇게 하면 초과금액이 항상 0 이 되어 검증이 무력화됩니다(§0-3). 승인금액 대체가 **맞는** 경우는 **두 축**입니다 — ① 교통비 등급제(`bstrCategoryType='GRADE'`, 교통비 전용) ② **지급구분이 실비 계열(`ACTUAL`·`ACTUAL_FIXED`)** — 이쪽은 전 용도 공통이고, **신청금액 자동충전**에서는 등급제보다 먼저 평가됩니다(`autofill-req-amount.ts:160-162` vs `:163-165`). 신청금액 **상한**(`receipt-amount-limit.ts`)에는 등급제 분기가 아예 없습니다. 그 밖에는 규정 조회·조건식 결과를 넣어야 합니다 |
| 3 | 1일 한도에 출장일수를 곱하면 된다 | `limitAmounts` 는 이미 **일자별 맵**입니다. 곱하지 않고 필요한 일자만 합산합니다. 급지가 섞이면 급지별로 나눠 호출해야 합니다 |
| 4 | 급지가 여러 개면 급지별 금액을 더한다 | 급지 간 병합은 합산이 아니라 **날짜별 `Math.max`** 입니다(per-diem 이중 계상 방지). 반면 **식비 동행인**은 합산입니다 — 병합 규칙이 반대입니다 |
| 5 | `matched: true` 면 그 조건을 전 일자에 적용한다 | 백엔드는 "적용될 일차가 **하나라도** 있는가"만 판정합니다. 40일 출장에 `lte 31` 조건이면 32~40일차에는 적용하지 않아야 합니다 |
| 6 | 조건 가드가 실패하면 그 날은 건너뛴다 | 가드 종류에 따라 정반대입니다. `dayType`·`dateRange`·`periodRange` 실패는 **건너뛰기(금액 유지)**, `calcMethod` 커버 실패(`isDayCovered=false`)는 **그 날 금액 0** 이며 앞선 조건 누적분까지 소멸합니다 |
| 7 | `dayTypeMap` 이 없으면 조건이 전부 적용된다 | **`dayType` 항목을 가진 「구체값」 조건만 불일치로 처리**됩니다(`calc-condition-guards.ts:29-41`). `dayType` 항목이 없는 조건과 와일드카드(`평일/공휴일`·빈 문자열)는 **그대로 적용**됩니다 |
| 8 | 외화는 조건을 적용한 뒤 환산하면 된다 | 순서가 반대입니다. **환산 → 조건 적용**입니다. 엔진이 **통화를 인식하지 않고** 조건의 피연산자에 통화 필드도 없어서, 순서를 바꾸면 외화 원금 위에 원화 값이 그대로 더해집니다 — 검산 예시 C 에서 약 **362배** 차이(통화 혼재). `max(0,·)`·절사의 비선형성은 그와 **별개의** 세 번째 사유입니다 → `02_조건식적용_규칙.md` §6-3 |
| 9 | 외화 증빙의 비교 통화는 하나다 | **판정 주체에 따라 갈립니다**(§1-3). 초과금액 컬럼·⑰ 은 **원화 환산끼리**(`overseasRuledAmount`·`foreignAmount` 미사용), ⑪·⑫ 는 **외화 원금끼리**(`foreignAmount` vs `overseasRuledAmount`)입니다 |
| 9-1 | 규정금액을 무엇과 비교하는지는 하나로 정해져 있다 | **두 축이 공존합니다** — 초과금액 컬럼·⑰ 은 **사용금액** 축, ⑪·⑫·화면 일별 판정은 **신청금액** 축입니다. 하나로 통일해 구현하면 우리 화면과 다른 판정이 납니다 → §1-3 |

| 19 | 응답에 없는 필드를 추가로 보내도 무시된다 | **요청 전체가 400** 입니다. `JacksonConfig` 가 `new ObjectMapper()` 를 직접 생성해 `FAIL_ON_UNKNOWN_PROPERTIES` 가 활성 상태입니다 → `05_자동증빙.md` §5.3.1 |
| 20 | 지급구분이 비면 신청금액 상한이 무제한이다 | 카드유형에 따라 갈립니다. `default` 분기에서 기타증빙(`ETC`)은 **`MIN(규정, 승인)`** 으로 오히려 엄격하고(규정금액 0 이면 한도 0), 카드 매입내역(비 `ETC`)만 무제한입니다 |

### 9-1. 증빙 3건의 금액 정합

| 증빙 | 용도 | 카드 | 지급구분 | 사용금액 | 규정금액 | 신청금액 | 초과금액<br>(사용금액 축) | ⑫ 판정<br>(신청금액 축) | `excessReason` |
|---|---|---|---|---:|---:|---:|---:|---|---|
| ① KTX | `TRANSPORT` | `CORP` | `LIMITED` | 47,000 | 60,000 | 47,000 | **0** | 이내 | `""` |
| ② 호텔 3박 | `ROOM` | `CORP` | `FIXED` | 180,000 | 130,000 | 180,000 | **50,000** | **초과** | **입력** |
| ③ 일비 (자동) | `DAILY_COST` | — | `FIXED` | 120,000 | 120,000 | 120,000 | **0** | 이내 | — |

- **① 신청금액이 47,000 인 이유** — `cardType='CORP'` 은 상한 우선순위 1위라 지급구분보다 먼저 걸립니다. 상한 = `approvalAmount` = 47,000. 규정금액 60,000 이 상한이 아닙니다.
- **② 를 법인카드로 둔 이유 (중요)** — `CORP` 는 상한이 `approvalAmount`(180,000)라 **신청금액이 규정금액을 넘을 수 있습니다.** 그래서 두 판정축이 **모두** 초과가 됩니다.
  - 사용금액 축(초과금액 컬럼 · ⑰): `MAX(0, 180,000 − 130,000)` = 50,000
  - 신청금액 축(⑫): `ruledAmount(130,000) < reqAmt(180,000)` → 초과 → `excessReason` 필수.
    ⚠️ **전제 두 개** — ① 관리자가 그 용도에 초과사유 설정을 **ON** 했고 ② 한도유형이 **`ONE_DAY`**(단건 비교)일 때입니다. `ALL` 이면 서버가 한도를 재조회하므로 증빙의 `ruledAmount` 와 무관해집니다
  - 규정 초과분을 법인카드로 결제한 뒤 초과분만 본인부담(미수금)으로 떼어내는 것이 실제 업무 흐름이며, 초과금액 분할(⑰)이 바로 그 기능입니다.
- **⚠️ 만약 ② 를 개인카드(`ETC`) + `FIXED` 로 두면 두 축이 갈립니다** — 상한이 `ruledAmount`(130,000)라 신청금액이 규정금액을 넘지 못하므로 **⑫ 는 발동하지 않고**(`130,000 < 130,000` = false) 초과금액 컬럼에만 50,000 이 남습니다. 이 경우 `excessReason` 은 요구되지 않고 ⑰(설정 ON 시)만 분할을 요구합니다. **같은 증빙, 같은 금액인데 판정이 갈리는 실제 예**입니다 → §1-3

### 9-3. 전표 금액(`slip`)은 신청금액에서 역산됩니다

비분할 증빙의 규칙입니다 (`bstr-policy/utils/compute-slip-amounts.ts` → `tax-integration/utils/vat-split-calculator.ts`).

- `slipAmt` = **`approvalAmount`** (사용금액). 신청금액이 아닙니다.
- `slipSplAmt` · `slipVatAmt` = 신청금액에서 분리합니다. **평가 순서 그대로** 씁니다.
  - ⓿ **신청금액 설정 미사용**(`isRequestAmountUsed = false`) → 영수증의 공급가액·부가세 그대로 (**첫 분기입니다** — 이 경우 신청금액에서 분리하지 않습니다)
  - 신청금액 == 승인금액 → 영수증의 공급가액·부가세 그대로
  - 신청금액 == 공급가액 → 공급가액 그대로 + 영수증 부가세
  - 영수증 부가세 == 0 → 신청금액 전액이 차변, 부가세 0
  - 그 밖(직접입력) → `공급가액 = ceil(신청금액 × 10 ÷ 11)`, `부가세 = 신청금액 − 공급가액`

샘플에서 실제로 갈린 결과입니다.

| 증빙 | 판정 | `slipAmt` | `slipSplAmt` | `slipVatAmt` |
|---|---|---:|---:|---:|
| ① | 신청 == 승인 → 영수증 값 그대로 | 47,000 | 42,727 | 4,273 |
| ② | 신청 == 승인 → 영수증 값 그대로 | 180,000 | 163,636 | 16,364 |
| ③ | 영수증 부가세 0 → 전액 차변 | 120,000 | 120,000 | 0 |

이 샘플은 세 건 모두 신청금액이 승인금액과 같거나 부가세가 0 이라 역산 경로를 타지 않습니다. **신청금액을 규정금액까지만 채우는 경우**(예: `ETC` + `FIXED`)에는 `10/11` 역산이 걸려 `공급가액 = ceil(신청금액 × 10 ÷ 11)`, `부가세 = 신청금액 − 공급가액` 이 되고, 그때 `slipAmt`(= 승인금액)와 `slipSplAmt + slipVatAmt`(= 신청금액)가 **달라지는 것이 정상**입니다 — 전표 총액은 사용금액이고 차변·부가세는 신청금액분입니다.
