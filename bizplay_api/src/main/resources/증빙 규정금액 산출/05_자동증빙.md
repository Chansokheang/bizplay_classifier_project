# §5 자동증빙의 규정금액

> 규정금액 3층 중, **시스템이 자동으로 만드는 증빙**(일비·유류비·통행료 등)의 규정금액을 다룬다.
> 사용자가 직접 등록하는 수동 증빙과 전송 배열·금액 시맨틱이 다르므로 따로 읽어야 한다.
>
> 이 문서의 모든 단정에는 `파일:행` 근거가 붙어 있다. 확인되지 않은 것은 `⚠️미확인` 으로 표시하고
> 문서 끝 「미확인 항목」 절에 모았다.

---

## 5.0 자동증빙과 수동 증빙은 전송 경로가 다르다

정산서 requestBody 에서 증빙은 **두 개의 다른 배열**로 나뉘어 실린다. 어느 배열에
실리는지가 규정금액의 산출 주체와 필드 계약을 전부 결정한다.

| | 수동 증빙 | 자동증빙 |
|---|---|---|
| 무엇 | 카드 매입내역 가져오기 · 기타/간이 영수증 등록 | 규정에 따라 시스템이 만드는 일비·유류비·통행료(·활동비 경로) |
| 생성 시점 | **문서보다 먼저** — 별도 API 로 Receipt 을 만들어 PK 확보 | **문서와 함께** — PK 가 없다 |
| 전송 필드 | `receiptIds` + `issuedFields` | **`etcReceiptSaveRequests`** |
| 전표 스냅샷(`bstrReceipts`) | 실린다 (PK 있음) | **실리지 않는다** (§5.5) |
| 사용금액의 출처 | 카드 승인금액(외부에서 들어온 사실) | **규정 산출액** (계산 결과) |

근거: 기존 공유자료 `../README.md:30` 「핵심 결론 3」 — "규정 자동증빙만 문서와 함께
생성(`etcReceiptSaveRequests`)되며, 전표 라인용 스냅샷(`bstrReceipts`)은 **PK 가 있는 증빙만**
실린다." 이 절은 그 결론을 코드로 재확인한 것이며, 상충하는 서술은 없다.

### 활동비에 대한 정정 — 5번째 `tranKindType` 이 아니다

「활동비」는 **독립된 자동증빙 종류가 아니다.** 활동비 정산유형이 실비(ACTUAL)일 때
일비 섹션이 렌더되지 않아 일비 자동증빙이 만들어지지 않는 갭을 메우기 위해, 같은
빌더로 **`DAILY_COST` 자동증빙 1건**을 섹션 밖에서 만드는 **경로**다
(`use-activity-actual-daily-receipt.ts:16-19`). 따라서:

- 필드·금액 계약은 일비와 100% 동일하다 (`use-activity-actual-daily-receipt.ts:257-275`).
- 외부에서 requestBody 를 조립할 때 **`tranKindType` 에 `'ACTIVITY'` 같은 값을 넣어서는 안 된다.**
  일비와 같은 `'DAILY_COST'` 다.
- 이 경로는 INNOTEK opt-in 이므로 **BZP 기본 테넌트에서는 동작하지 않는다**
  (`use-activity-actual-daily-receipt.ts:2-3,113-121`).

## 5.2 「규정금액이 곧 발생금액」 구조

### 자동증빙은 4개 금액 필드에 같은 값을 넣는다

세 빌더 모두 산출한 총액 하나(`totalAmount` / `defaultAmount` / `tollFare`)를
**승인금액·공급가액·규정금액·신청금액에 그대로 대입**한다.

| 자동증빙 | 대입 코드 | 근거 |
|---|---|---|
| 일비 | `approvalAmount = settleAmount = reqAmt = ruledAmount = supplyAmount = totalAmount` | `daily-cost-receipt-builder.ts:157-161` · `auto-receipt-utils.ts:185-189` |
| 유류비 | `approvalAmount = supplyAmount = ruledAmount = reqAmt = defaultAmount` | `fuel-cost-receipt-creator.ts:199-202` |
| 통행료 | `approvalAmount = supplyAmount = ruledAmount = reqAmt = tollFare` | `toll-cost-receipt-creator.ts:193-196` |
| 직원숙소 | `approvalAmount = settleAmount = reqAmt = ruledAmount = supplyAmount = totalAmount` | `auto-receipt-utils.ts:344-350` |

즉 **규정금액 = 사용금액 = 신청금액**이므로 구조적으로 초과금액
(`MAX(0, 사용금액 − 규정금액)`)이 항상 0 이다. 자동증빙에 초과사유가 요구되지 않는
이유가 여기 있다.

부가세는 자동증빙 빌더에서 세팅하지 않는다 — 변환기가 `vatAmount ?? 0` 으로 0 을
넣고 `supplyAmount` 를 그대로 쓴다 (`expense-report-save-utils.ts:134` · 유류비·통행료는
`nonDeduction: true` 로 불공제 기준 세금코드를 조회한다 —
`fuel-cost-receipt-creator.ts:178-184,206` · `toll-cost-receipt-creator.ts:172-178,199`).

### 수동 증빙과의 대비

| 축 | 수동 증빙 | 자동증빙 |
|---|---|---|
| 사용금액(`approvalAmount`) | **카드 승인금액** — 외부에서 들어온 사실. 프론트가 계산하지 않는다 | **규정 산출액** — 프론트가 계산한다 |
| 규정금액(`ruledAmount`) | 별도 규정 조회 결과. 사용금액과 무관하게 정해진다 | 사용금액과 **동일한 값** |
| 신청금액(`reqAmt`) | 규정 cap 에 걸려 `MIN(사용금액, 규정금액)` 계열로 자동충전 | 사용금액과 **동일한 값** |
| 초과금액 | `MAX(0, 사용금액 − 규정금액)` — 0 이 아닐 수 있다 | 구조적으로 **항상 0** |
| 초과사유 | 초과 시 필수(검증 ⑫) | 해당 없음 |
| 사용자 수정 | 신청금액 셀 등 편집 가능 | `documentBound: true` — 분할 비활성 · 삭제 아이콘 숨김 (`auto-receipt-utils.ts:310-312`) |
| 전송 배열 | `receiptIds` + `issuedFields` | `etcReceiptSaveRequests` |
| PK | 있다 | **없다** (문서와 함께 생성) |

> ⚠️ **외부 조립 시 주의 — ⑪·⑫ 는 「신청금액 축」이다.**
> `MAX(0, 사용금액 − 규정금액)`(초과금액 컬럼·⑰)과 축이 다르다. ⑪·⑫ 는
> **`reqAmt` 가 `ruledAmount` 를 넘는지**로 판정한다
> (`utils/validation/exceed-check-utils.ts:156` · `utils/validation/validate-total-exceed.ts:110`·`:195`;
> 단 지급기준이 `ACTUAL` 계열이면 `approvalAmount` 축 — `exceed-check-utils.ts:144`·`:153`).
> 자동증빙이 네 필드를 같은 값으로 채우면 `reqAmt == ruledAmount` 라 ⑪·⑫ 도 함께 성립하지 않는다.
> **다만 식비·잡비는 예외다 — 바로 아래 절을 볼 것.**

### ★ 예외 — 식비(FOOD)·잡비(INCIDENTAL)는 `ruledAmount` 가 「1일 단가」다

`createFixedCostReceipt`(`utils/auto-receipt-utils.ts:253-258`)는 금액을 이렇게 넣는다.

| 필드 | 값 |
|---|---|
| `approvalAmount` · `settleAmount` · `reqAmt` · `supplyAmount` | **한도 × 일수** (총액) |
| `ruledAmount` | **`limitAmount`** — 1일 단가 그대로 |

**그래서 2일 이상이면 `reqAmt > ruledAmount` 가 되어 위 신청금액 축에서 초과가 성립한다.**
예: 1일 한도 20,000 · 3일 → `reqAmt = 60,000`, `ruledAmount = 20,000` → ⑪·⑫ 발동 대상.

앞 절의 「규정금액 = 사용금액 = 신청금액」은 **일비·유류비·통행료·직원숙소 4종에만** 해당한다.
직원숙소는 `auto-receipt-utils.ts:347-348` 주석이 "`ruledAmount` = 한도 합산(일비 패턴)"이라며
**의도적으로 총액으로 고쳐** 놓았으므로, 단가 시맨틱이 남은 것은 **식비·잡비 둘뿐**이다.

> 외부에서 식비·잡비 자동증빙을 조립한다면 `ruledAmount` 를 총액으로 넣을지 단가로 넣을지가
> ⑪·⑫ 발동을 가른다. 현행 화면 동작과 맞추려면 **단가**를 넣어야 하고, 그러면 초과사유가
> 요구될 수 있다. 이 비대칭이 의도인지는 저희가 확인해 회신하겠습니다(§미확인 M-6).

### 자동증빙의 `slip` 기본값은 빌더가 아니라 별도 단계가 채운다

일비·식비·잡비·숙박 자동증빙의 `slip.accountSubjectId` · `taxCodeId` · `taxName` · `summary` ·
`branchOfficeId` · `internalOrderId` 는 **빌더가 비워 두고**
`enrichAutoReceiptsWithDefaults`(`utils/autofill-batch.ts:62`, 호출
`hooks/use-expense-report-rule-effects.ts:200`)가 채운다. 유류비·통행료만 creator 안에서 직접
조회한다.

> ⚠️ **이 단계가 `vatAmount`·`supplyAmount` 를 다시 계산하는 테넌트가 있다.**
> `vatBasedDeductionEnabled = false`(INNOTEK·KSOE)면 `calculateVatAndSupply` 로 재계산하므로
> (`utils/autofill-batch.ts:213-223`) **공급가액 ≠ 승인금액**이 되고, 앞 절의 「4개 금액 필드에
> 같은 값」과 필드표의 「`vatAmount` 는 실질 미설정」이 그 테넌트에서 깨진다.
> 이 문서의 금액 서술은 **BZP 기준**이다.

## 5.3 `etcReceiptSaveRequests` 필드 매핑표

### 5.3.1 ★ 경고 — DTO 에 없는 필드 하나로 요청 전체가 400 이다

백엔드 `JacksonConfig` 가 `@Primary ObjectMapper` 를 **`new ObjectMapper()` 로 직접
생성**한다.

```java
// backend/app-internal-api/src/main/java/com/newbizplay/config/JacksonConfig.java:17-24
@Bean
@Primary
public ObjectMapper primaryObjectMapper() {
    ObjectMapper objectMapper = new ObjectMapper();
    objectMapper.registerModule(new JavaTimeModule());
    objectMapper.disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);
    return objectMapper;
}
```

의미:

- Spring Boot 는 자동구성된 `Jackson2ObjectMapperBuilder` 로 만든 매퍼에 대해
  `DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES` 를 **끄는** 것이 기본값이다.
- 그런데 위 코드는 그 빌더를 경유하지 않고 `new ObjectMapper()` 를 직접 만든 뒤
  `@Primary` 로 등록한다. **Jackson 자체 기본값은 `FAIL_ON_UNKNOWN_PROPERTIES = 활성`**
  이며, 이 코드에는 그것을 끄는 `disable(...)` 호출이 없다
  (파일 전체 39줄에 `DeserializationFeature` 를 만지는 줄이 하나도 없다). 같은 파일에 두 번째 `ObjectMapper` 빈(`customObjectMapper`, `:26-36`)이 있으나 `@Primary` 가 아니라 요청 역직렬화에 쓰이지 않으므로 결론은 같다.
- 따라서 **DTO 에 선언되지 않은 필드가 하나만 섞여도 그 요청 전체가 400** 이 된다.
  일부 필드가 무시되는 식의 부분 성공은 없다.

프론트 타입 파일 머리말도 같은 사실을 못박고 있다 —
"서버에 없는 필드(`useDate`, `settleAmount`, `cardType` 등)를 보내면 Jackson 에러가
발생하므로 백엔드 DTO와 1:1로 유지한다" (`bstr-policy/save-request-types.ts:8-9`).

## 5.4 일비의 별도 경로 — 일별 규정금액과 소수점 처리

### 5.4.1 두 경로가 있고, 갈림길은 「일자별 맵을 SoT 로 쓸 이유가 있는가」다

`resolveDailyCostRuledAmount` (`utils/daily-cost-amount-utils.ts:321-418`)가 판정한다.
아래 셋 중 **하나라도** 참이면 일자별 합산 경로, 셋 다 거짓이면 스칼라 폴백이다
(`:337-351`).

| 조건 | 판정 | 근거 |
|---|---|---|
| 활성 계산식 존재 | `appliedConditions` 중 `matched && !overridden` 1건 이상 | `:337-339` |
| 차등지급 | `rule.payType === 'DIFF'` — 스칼라 `limitAmount` 가 0 이고 첫날/마지막날 금액이 맵에만 있다 | `:344` |
| 지급옵션 축소 | 선택일 중 `limitAmounts[date] == null` 인 날이 1일 이상 (`EXCEPT_START`/`FIX_TWO_DAYS` 등이 백엔드에서 날짜를 제거) | `:350` |

또 `limitAmounts` 가 비었거나 `rule.calcEnabled === false` 면 즉시 스칼라 폴백이다 (`:332-334`).

### 5.4.2 일자별 합산 경로의 실행 순서 (5단계)

```
① 차등금액(diffCurrency) 외화 환산       resolveDiffCurrencyRates → applyDiffCurrencyToRule
      ↓                                  daily-cost-amount-utils.ts:357-369
② 외화면 일자별 KRW 환산 (base 맵 생성)   exchangeToKRW(amount, currencyCode, rate) 를 날짜마다
      ↓                                  :374-396   (환율 실패 → null 반환 = 스칼라 폴백 위임 :386-392)

③ 계산식 엔진 재적용 (KRW base 위)        applyCalcConditionsKRW(convertedRule, krwBaseMap, opts)

      ↓                                  :411-413
```

**순서를 뒤집으면 안 된다** — ②(환산) 다음에 ③(계산식)이다. 외화 규정에 계산식이 있으면
조회 시점에 엔진이 보류되어 `limitAmounts` 에 외화 원본이 남아 있으므로, 환산 후 KRW base
위에서 엔진을 재적용해야 통화가 섞이지 않는다 (`:302-314`).

### 5.4.3 ★ 소수점 처리 위치 — 정확히 어디인가

**합계가 아니라 「일자별」이다. 처리 방식은 `Math.trunc` (0 방향 버림)이며, 처리 위치는
`packages/domains/src/cloud-expense-report/utils/daily-cost-amount-utils.ts:413` 이다.**

```ts
// daily-cost-amount-utils.ts:410-414
for (const [date, amount] of Object.entries(finalMap)) {
  // 규칙: 엔진 무반올림 → 일자별 원 단위 버림(Math.trunc) 후 합산 (레거시 "조건 반영 후 일자별 floor" 정합).
  //   미절삭 시 정수 KRW base × 50% 등에서 0.5원이 영수증·라벨까지 유출된다(예: 121,972.5원).
  if (eligibleSet.has(date)) totalAmount += Math.trunc(amount);
}
```

- **왜 일자별인가** — 레거시 정합이다. 레거시는 조건 반영이 끝난 **일자별** 금액에
  `Math.floor` 를 최종 적용했다 (`daily-cost-amount-utils.ts:248-250` 주석,
  레거시 `SeahExpenseReportUtils` 1631 인용). 합계에 한 번 적용하면 값이 달라진다.
- **왜 `floor` 가 아니라 `trunc` 인가** — `Math.floor` 는 음수에서 절대값이 1원 커져
  원거래·취소 쌍의 합이 어긋난다 (`bstr-policy/utils/currency-utils.ts:53-55`).
- **미절삭 시 증상** — 정수 KRW base × 50% 등에서 0.5원이 영수증·라벨까지 유출된다
  (예: 121,972.5원) (`:412` 주석).

같은 규칙이 적용되는 지점은 도메인 전체에 **5곳**이며(계획서 경로 `business-plan/utils/bstr-plan-limit-enrich.ts:120` 포함 — 그 주석 `:116-119` 이 「정산서 정본과 같은 절삭이라 계획서=정산서 금액 일치가 유지된다」고 명시한다) 모두 「일자별 `Math.trunc`」로
통일돼 있다. 한쪽만 고치면 금액과 표기·일수가 어긋난다.

| 지점 | 용도 | 근거 |
|---|---|---|
| `daily-cost-amount-utils.ts:413` | **자동증빙 금액(정본)** — 일자별 합산 경로의 총액 | `resolveDailyCostRuledAmount` |
| `daily-cost-amount-utils.ts:251` | 라벨 표기 금액(증빙 미생성 폴백) | `calcRuleBasedDailyCostLabelAmount` |
| `daily-cost-amount-utils.ts:288` | **지급일수** — 버림으로 0원이 된 날을 일수에서도 뺀다 | `calcRuleBasedDailyCostPaidDayCount` |
| `daily-cost-breakdown.ts:141,146` | 산출내역 툴팁의 일자별 표기 (KRW 규정만) | `buildDailyCostBreakdown` |

### 5.4.4 스칼라 폴백 경로의 소수점

스칼라 경로는 **`Math.trunc` 를 쓰지 않는다.** 대신 환산 단계 내부에서 처리된다.

```
convertDailyCostUnitToKRW(limitAmount, currencyCode, dates)      daily-cost-amount-utils.ts:168-209
  KRW → 원금 그대로 (환산 skip)                                   :177-180
  외화 → exchangeToKRW(limitAmount, currencyCode, rate)            :207
           = Math.trunc(amount × rate)  또는  JPY/IDR/VND 는 Math.trunc(amount × rate / 100)
                                                                  bstr-policy/utils/currency-utils.ts:64,66
  환율 실패 → 원금 유지 폴백 (NaN 방지)                            :196-204
총액 = krwUnit × 유효 일수                                        daily-cost-receipt-builder.ts:136
```

즉 스칼라 경로는 **단가에 1회 버림**하고 일수를 곱한다. 외부에서 재현할 때
`exchangeToKRW` 밖에서 추가 `floor` 를 적용하면 이중 절삭이 된다
(`daily-cost-amount-utils.ts:156-158` 주석 — "외부에서 추가 floor 적용 금지").

### 5.4.5 환율 조회기는 규정금액 검증과 반드시 같아야 한다

일비는 **규정금액 = 신청금액**이므로, 자동증빙 금액과 규정금액 검증이 서로 다른 환율을
쓰면 「신청금액 > 규정금액」이 되어 총액초과가 오판정된다. 그래서 두 경로가 같은 조회기
(`fetchCachedExchangeRateWithSetting`, `businessType='BSTR'`, `useExceptionTiming: true`)를
쓰도록 고정 주입되어 있다.

- 자동증빙 금액: `daily-cost-amount-utils.ts:182-192,357-368,376-385`
- 규정금액 검증: `utils/validation/daily-ruled-amount-utils.ts:29-36` — 머리말이 그 이유를
  명시한다 (`:8-10`).

`daily-ruled-amount-utils.ts` 자체는 **얇은 래퍼**다 (62줄). 계산 정본은
`bstr-policy` 로 이동했고 (`fetchDailyRuledAmount` → `bstr-policy/utils/ruled-amount-calculator.ts`),
이 파일은 정산서 전용 의존성 2개(환율 조회기 `fetchCachedExchangeRateWithSetting`,
허용일수 조회기 `fetchAllowBeyondDays`)만 주입한다 (`:16-36,44-51,57-62`).

## 5.5 자동증빙은 `bstrReceipts` 에 실리지 않는다

전표 라인용 스냅샷 배열 `bstrReceipts` 의 구성은 **PK 필터가 게이트**다.

```ts
// utils/prepare-save-data.ts:176-177
const bstrReceipts = allReceipts
  .filter((r) => r.id != null && (isPrepaymentNegativeReceipt(r) || (r.id > 0 && issuedIdSet.has(r.id))))
```

- 입력은 `allReceipts` = `store.receipts`(수동 증빙 4그룹 flat)뿐이다 —
  `autoReceipts` 는 이 배열에 **들어가지 않는다** (`prepare-save-data.ts:128-133`).
- 조건 `r.id != null && r.id > 0 && issuedIdSet.has(r.id)` — **PK 가 있고, 그 PK 가
  `issuedFields` 조회 결과에 실제로 존재하는 증빙만** 통과한다
  (`issuedIdSet` 구성: `:141-151`).
- 자동증빙은 문서와 함께 생성되므로 PK 가 없다 → 두 이유로(배열 자체가 다르고, PK 필터도
  통과 못 한다) `bstrReceipts` 에 실릴 수 없다.
- 유일한 예외는 **선지급 반제 -증빙**이다 — `isPrepaymentNegativeReceipt(r)` 로
  `issuedIdSet` 게이트를 우회해 음수 id 증빙도 싣는다 (EACC 회계 전표 상계 라인 생성용,
  `:171-175`). 단 이것은 복원 경로(M-2/M-3)에서 `store.receipts` 에 이미 있는 것이고,
  신규 생성 반제는 `etcReceiptSaveRequests` 쪽에 붙으며 음수 id 를 만들지 않아
  `bstrReceipts` 에 실리지 않는다 (`:277-280`).

**기존 공유자료 `../README.md` 와의 일치** ✅

|---|---|---|
| `../README.md:30` (핵심 결론 3) | "규정 자동증빙만 문서와 함께 생성(`etcReceiptSaveRequests`)되며, 전표 라인용 스냅샷(`bstrReceipts`)은 **PK 가 있는 증빙만** 실린다" | 코드와 일치 |

### 상위 진입점

`buildExpenseReportSavePayload` (`expense-report-save-utils.ts:219-273`)가
`prepareExpenseReportSaveData` 를 감싼다. 자동증빙과 관련해 여기서만 하는 일:

1. `fetchRequestedAmountSetting()` 으로 **신청금액 설정**(`requestedAmountUsed`)을 조회
   (실패 시 `false` 폴백) — 이 값이 C-1 의 slip 금액 역산 축을 바꾼다 (`:253-254,268-270`).
2. **수동** 증빙에 대해서만 `buildIssuedFields(receipts, isRequestAmountUsed)` 를 호출
   (`:255`). 자동증빙은 이 경로를 타지 않는다.

### ⚠️ 외화 필드 3개가 저장 payload 에서 탈락한다

빌더는 외화 자동증빙(일비)에 `overseasRuledAmount`·`overseasApprovalAmount`·`overseasUsed`
를 세팅한다 (`daily-cost-receipt-builder.ts:176-189` · `auto-receipt-utils.ts:197-200`).
DTO 에도 세 필드가 선언되어 있다 (`save-request-types.ts:28,29,34` · 백엔드
`EtcReceiptSaveRequest.java:60,62,127`).

그런데 `toEtcReceiptSaveRequests` 의 반환 객체에 이 세 키가 **없다**
(`expense-report-save-utils.ts:143-199` 전수 확인). 즉 스토어에는 있지만 저장 요청에는
실리지 않는다. `exchangeRate`·`currencyCode` 는 전송된다 (`:156,166`).

이것이 의도인지(계산식 적용 외화는 KRW 로 통일 표기하므로 `overseasRuledAmount` 를
`null` 로 두는 D3 규칙 — `daily-cost-receipt-builder.ts:125,183-189`의 연장선인지)
누락인지는 코드 주석으로 확정할 수 없었다 → **미확인 M-1**.
