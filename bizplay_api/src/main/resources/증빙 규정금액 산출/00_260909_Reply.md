## 1. Cause — the ruled amount is a computed result, not an API response

There are three layers between the API and the ruled amount that ends up on a receipt.

| Layer | What it does | Owner |
|---|---|---|
| ① Raw data lookup | Returns the **base amount** by expense purpose, grade zone, and period | Our backend `POST /api/v2/bstr/policy/renewal/limit` |
| ② Condition application | Applies the response's `appliedConditions[]` **per day** to produce the final ruled amount | **The caller** |
| ③ Validation | Excess-amount calculation, claim-amount cap, submission blocking | The caller |

**② is the caller's responsibility.** The backend only decides *which conditions apply* and returns them; it does not perform the arithmetic that applies those conditions to the amount.

## 2. ⚠️ Our Swagger description was written backwards from the implementation

```
BstrPolicyRenewalController  (Swagger description)  "returns the final amount with adjustments applied"   ← WRONG
BstrRenewalLimitService                              limitAmounts stays as the base amount               ← ACTUAL IMPLEMENTATION
```

**Building against the API documentation alone was guaranteed to produce a wrong result.** If you were reading the response's `limitAmounts` as the final ruled amount, this description is the reason. We apologize for the confusion, and we will correct it.

## 3. The sample we sent had the same gap

These are the values from the `정산서_requestBody_샘플.json` (settlement requestBody sample) we sent previously.

| Receipt | Purpose | Approved amount | Ruled amount | Payment type |
|---|---|---:|---:|---|
| `bstrReceipts[0]` | Transportation | 47,000 | **0** | **null** |
| `bstrReceipts[1]` | Meals | 24,000 | 30,000 | **null** |

The transportation ruled amount was `0`, and the payment type was empty on both manual receipts.
**You followed the sample exactly**, and filling in `ruledAmount = approvalAmount` in the 260819 revision appears to be a continuation of that.

Setting the ruled amount equal to the approved amount makes `excess = MAX(0, usedAmount − ruledAmount)` **structurally always 0**, so any validation that depends on the excess never makes a determination at all. Note, however, that **not everything passes** — only the per-item determination is neutralized, while aggregate determinations (lodging/meal total overruns, etc.) still work. That is likely why the symptom looked like "sometimes it validates and sometimes it doesn't" rather than "validation is entirely missing."

## 5. ★ Please do use the golden vectors

② (condition application) has many rules, so **an implementation can easily drift even when the prose is understood correctly.**
We therefore ran our own engine and extracted **71 input↔output pairs** to send along.

```
1. Feed each vector's input (+opts / krwBaseMap) into your ② implementation.
2. Compare the resulting per-day amounts against expected.limitAmounts.
3. If they differ, the vector's group and description tell you which rule diverged.
```

They cover all 8 operators, all 6 calcMethods, weekday filters, date/period options, tiered calculation, travel days, accumulation order, override fallback, and foreign-currency re-application.

> **We got two things wrong ourselves while building these vectors.** `fixed` and `silbiLimit` use `fixedAmount`, not `operatorValue`, and when that value is absent they **leave the amount unchanged** (not 0). The rules were written correctly in the documentation, yet the implementation still diverged, and comparing against the vectors exposed it immediately.
> That is why we strongly recommend this step.
