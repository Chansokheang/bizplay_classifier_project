# §3. 조건식 적용 규칙 (규정금액 3층 中 ②층)

> **이 절의 위치** — 규정금액은 3층이다.
> ① 원자료 조회: 백엔드 `POST /api/v2/bstr/policy/renewal/limit` → `limitAmounts`(일자별 **기준금액**) + `appliedConditions[]`(조건식) + `dayTypeMap`
> ② **조건식 적용 (이 문서)** — 프론트가 기준금액 위에 조건을 일자별로 얹어 최종 규정금액을 만든다
> ③ 검증: 증빙 금액 ≤ 규정금액
>
> 백엔드는 **금액을 계산하지 않는다.** `BstrRenewalLimitService.java:149` 주석이 정본이다 —
> 「limitAmounts는 기준금액 그대로 유지 (프론트가 조건 적용하여 최종 금액 산출)」
> 따라서 외부 시스템이 requestBody 를 직접 조립할 때 `ruledAmount` 를 채우려면 **이 문서의 계산을 자기 쪽에서 재현해야 한다.**

## 1. 적용 순서 (알고리즘)

### 1-0. 대전제 4가지

| # | 규칙 | 근거 |
|---|------|------|
| 1 | **반올림하지 않는다.** 모든 연산은 실수 그대로. 반올림·floor·trunc 는 표시·영수증 단계 책임이다. | `calc-condition-engine.ts:8` (엔진 머리말) |
| 2 | 루프는 **일자가 외부, 조건이 내부**다. | `calc-condition-engine.ts:399`(일자) → `:222`(조건) |
| 3 | 같은 날 안에서는 **이전 조건의 결과 금액에 다음 조건을 얹는다**(누적). 날짜 간에는 누적하지 않는다 — 각 날은 `limitAmounts[date]` 에서 새로 시작한다. | `calc-condition-engine.ts:221`(`result = amount`) · `:229`·`:232`(`result` 재대입) · `:401` |
| 4 | 순회 순서는 `sortOrder` 오름차순. 같은 `sortOrder` 는 응답 배열 순서를 유지한다(`Array.sort` 안정 정렬). | `calc-condition-engine.ts:334` |

규칙 3 때문에 **조건 순서가 결과를 바꾼다.** 테스트가 이를 명시적으로 고정한다 —
`×2` 다음 `정액 10,000` = **10,000** / `정액 10,000` 다음 `×2` = **20,000** (`calc-condition-engine.test.ts:104-131`).

### 1-1. 의사코드 — 최상위

```text
FUNCTION applyCalcConditions(response, opts = {}) -> response'
  conditions ← response.appliedConditions
  baseMap    ← response.limitAmounts          // { "YYYY-MM-DD": 기준금액 }

  # 가드 (패스스루 — limitAmounts 원본 유지)
  IF conditions is null OR conditions is empty OR baseMap is null:  RETURN response   # :319
  IF response.calcEnabled === false:                                RETURN response   # :320

  # 대상 조건 선정: matched 인 것만. sortOrder 오름차순.
  #   ※ overridden 은 여기서 제외하지 않는다 — 일자별로 판정한다(§1-3).
  candidates ← conditions.filter(c => c.matched === true)
                         .sort(asc by c.sortOrder)                                    # :332-334

  IF candidates is empty:
      RETURN response with calcBreakdown = {                                          # :335-340
          baseAmount : response.limitAmount ?? 0,
          items      : [],
          totalAmount: sum(values(baseMap))
      }
      # limitAmounts 는 손대지 않는다.

  dates ← sort(keys(baseMap))                 // ISO 문자열 정렬 = 시간순             # :354

  (positions, isTravelDayAssignable)
      ← resolveDayPositions(dates, opts.preCount ?? 0, opts.postCount ?? 0,
                            response.calcPeriod)                                      # :364

  # 조건을 이동일/코어로 3분할 — §5
  IF isTravelDayAssignable:                                                           # :371-379
      preConds  ← candidates where hasItemType(c, opts.predepartType)
      postConds ← candidates where hasItemType(c, opts.nextarriveType)
      coreConds ← candidates where NOT hasItemType(c, predepartType)
                                AND NOT hasItemType(c, nextarriveType)
  ELSE:
      preConds ← []  ;  postConds ← []  ;  coreConds ← candidates

  dayTypeMap ← response.dayTypeMap ?? {}                                              # :394
  finalMap   ← {}
  appliedSet ← ∅                              // 산출내역(calcBreakdown) 표기용

  FOR index, date IN enumerate(dates):                                                # :399
      amount ← baseMap[date] ?? 0
      pos    ← positions[date]
      IF pos is missing:  finalMap[date] ← amount ; CONTINUE                          # :404-407

      dayNum ← index + 1                      // ★ 맵 인덱스 기준. 절대 날짜 아님 — §3-3  # :410

      IF pos.slot == 'pre':                                                           # :411-415
          finalMap[date] ← applyConditionsForDay(preConds,  date, amount, dayTypeMap,
                                                 isFirst=TRUE,  isLast=FALSE,
                                                 dayNum, pos=NONE, appliedSet)
      ELSE IF pos.slot == 'post':                                                     # :416-420

                                                 isFirst=FALSE, isLast=TRUE,
                                                 dayNum, pos=NONE, appliedSet)
      ELSE:  // 'core'                                                                # :421-434
          finalMap[date] ← applyConditionsForDay(coreConds, date, amount, dayTypeMap,
                                                 isFirst=pos.isFirst, isLast=pos.isLast,
                                                 dayNum, pos=pos, appliedSet)

  RETURN response with
      limitAmounts  = finalMap,
      calcBreakdown = buildBreakdown(response.limitAmount ?? 0,
                                     sort(appliedSet, asc by sortOrder),
                                     sum(values(finalMap)))                           # :437-450
```

### 1-2. 의사코드 — 하루치 (`applyConditionsForDay`, `:203-236`)

```text
FUNCTION applyConditionsForDay(conds, date, amount, dayTypeMap,
                               isFirst, isLast, dayNum, pos, appliedSet) -> number

  # 1단계: 이 날 "적용 가능한" 조건 id 집합 — 일별 fallback 판정의 기준
  applicableIds ← { c.id | c ∈ conds, c.id ≠ null,
                    isApplicableOnDay(c, date, dayTypeMap, dayNum) }                  # :215-220

  # 2단계: 순서대로 얹기
  result ← amount                                                                     # :221
  FOR cond IN conds:                          // 이미 sortOrder 오름차순              # :222
      IF NOT isApplicableOnDay(cond, date, dayTypeMap, dayNum):  CONTINUE             # :223
      IF isSuppressedOnDay(cond, applicableIds):                 CONTINUE             # :225
      appliedSet.add(cond)                                                            # :226
      IF pos is present:                      // 코어일                              # :227-230
          result ← isDayCovered(cond, pos) ? calculateAmount(cond, result, isFirst, isLast)
                                           : 0                  // ★ 스킵이 아니라 0
      ELSE:                                   // 이동일(pre/post) — 커버 판정 생략      # :231-233
          result ← calculateAmount(cond, result, isFirst, isLast)
  RETURN result


FUNCTION isApplicableOnDay(cond, date, dayTypeMap, dayNum) -> boolean                 # :167-178
  RETURN isDayTypeMatched(cond, dayTypeMap[date])      # §3-1
     AND isDateInRange(cond, date)                     # §3-2
     AND isPeriodDayCovered(cond, dayNum)              # §3-3


FUNCTION calculateAmount(cond, amount, isFirst, isLast) -> number                     # :151-161
  IF normalizeMethod(cond.calcMethod) == 'dailyDiff':
      RETURN applyDailyDiff(cond, amount, isFirst, isLast)      # §4 — operator 무시
  RETURN applyOperator(cond, amount)                            # §2
```

> **⚠️ 가장 틀리기 쉬운 지점** — 코어일에서 `isDayCovered(cond, pos)` 가 false 이면
> **그 조건을 건너뛰는 것이 아니라 그 날 누적금액을 0 으로 만든다**(`:228-230`).
> 즉 앞선 조건들이 만들어 둔 값까지 함께 소멸한다.
> 예: `departArrive` 조건 1개 · 3일 → `[100, 0, 100]` (`calc-condition-engine.test.ts:173-176`).

### 1-3. `overridden` / `supersededByIds` — 일별 fallback

```text
FUNCTION isSuppressedOnDay(cond, applicableIds) -> boolean                            # :187-191
  superseders ← cond.supersededByIds
  IF superseders == null:                          // 구버전 백엔드 (미전달)
      RETURN cond.overridden === true              //   → 전역 미적용 (하위호환)
  RETURN ∃ id ∈ superseders : id ∈ applicableIds   // 신버전: 그 날 상위가 있으면 밀림
```

의미:

- `supersededByIds` = 이 조건을 strict-superset(더 구체)하여 우선하는 **상위 조건 id 목록** (`renewal-limit-api.ts:243-246`).
- 그 상위 조건이 **그 날** 적용 가능하면 이 조건은 밀린다(미적용). 상위가 그 날 전부 미적용이면 **이 조건이 이어받는다(fallback)**.
- `overridden` 은 "덮는 상위가 존재함"의 요약 플래그일 뿐 "전역 미적용"이 아니다 (`renewal-limit-api.ts:240-242`). `overridden=true` 여도 적용될 수 있다.

체인 예시 (`calc-condition-engine.test.ts:906-936`, A→B→C):

| 날짜 | 요일유형 | A(id3, 평일 + 1/1 한정, 10,000) | B(id2, 평일, 8,000) | C(id1, 전체, 5,000) | 결과 |
|------|---------|------------------------------|-------------------|-------------------|------|
| 2026-01-01 | 평일 | 적용 | A에 밀림 | A·B에 밀림 | **10,000** |
| 2026-01-02 | 평일 | dateRange 밖 → 미적용 | 적용(이어받음) | B에 밀림 | **8,000** |
| 2026-01-03 | 주말 | dayType 불일치 → 미적용 | dayType 불일치 → 미적용 | 적용(이어받음) | **5,000** |

> **외부 시스템이 구버전 계약만 재현할 수도 있다.** `supersededByIds` 를 무시하고
> `matched && !overridden` 으로 필터하면 위 표의 1/2·1/3 이 "조건 없음"(기준금액 23,000)이 되어 어긋난다.
> `supersededByIds` 가 응답에 있으면 **반드시** 일별 판정을 구현해야 한다.

### 1-4. 멱등 가드 — 두 번 적용하면 금액이 틀어진다

엔진 자체에는 멱등 가드가 **없다.** `applyCalcConditions` 는 부르는 만큼 계산한다.
가드는 **소비 경로**에 있다.

```text
isCalcAlreadyApplied ← (rule.calcBreakdown 존재) AND (rule.calcDeferred 가 truthy 아님)
IF isCalcAlreadyApplied:  limitAmounts 를 그대로 쓴다 (엔진 재호출 금지)
ELSE:                     applyCalcConditionsKRW(rule, {...limitAmounts}, opts) 로 1회 적용
```

| 위치 | 행 |
|------|----|
| `cloud-expense-report/utils/daily-cost-amount-utils.ts` | `:240-243`, `:278-281` |
| `cloud-expense-report/utils/daily-cost-breakdown.ts` | `:132-135` (근거 주석 `:99-102`) |

즉 **`calcBreakdown` 이 있고 `calcDeferred` 가 아니면 = 이미 적용 완료**다.
`calcDeferred=true` 는 "기준금액은 raw, 산출내역만 먼저 만들어 둔 상태"를 뜻한다(§5-3, §6).

## 2. `operator` 8종 연산 규칙

### 2-1. 값 집합

`OPERATOR` 상수 (`calc-condition-engine.ts:25-34`) — 관리자 화면의 `CALC_OPERATORS`
(`bstr-expense-rule/constants/calc-constants.ts:238-248`)와 **8개가 1:1로 일치**한다.

| operator | 관리자 라벨 | 수식 (`amount` = 그 날까지의 누적금액) | 설명 | 근거 행 |
|----------|------------|--------------------------------------|------|---------|
| `none` | 미적용 | `amount` | 금액 변경 없음 | `:121-122` |
| `unpaid` | 미지급 | `0` | 그 날 미지급 | `:123-124` |
| `fixed` | 정액 | `cond.fixedAmount != null ? cond.fixedAmount : amount` | 누적금액을 **대체**(가감 아님) | `:125-126` |
| `silbiLimit` | 실비(제한) | `cond.fixedAmount != null ? cond.fixedAmount : amount` | 한도금액까지만 실비. **`min` 이 아니라 `fixed` 와 동일한 대체** | `:127-130` |
| `x` | × | `isPercent ? amount × (v / 100) : amount × v` | `isPercent` = §2-3 | `:131-136` |
| `+` | + | `amount + v` | | `:137-138` |
| `-` | − | `max(0, amount − v)` | **하한 0 클램프** | `:139-140` |
| `/` | ÷ | `v !== 0 ? amount / v : amount` | 0 나눗셈은 금액 유지 | `:141-144` |
| (그 외 문자열) | — | `amount` | 미지의 operator 는 무변경 | `:145-146` |

`v` = `parseValue(cond.operatorValue)` (§2-4).

주의 3가지:

1. **`silbiLimit` 은 `min` 이 아니다.** 한도금액이 기준금액보다 커도 대체한다 —
   기준금액 10,000 + `silbiLimit` 16,500 → **16,500** (`calc-condition-engine.test.ts:1020-1022`).
   초과분 미지급은 이 한도를 기준으로 **하위 초과판정**이 처리한다(`:128-130` 주석).
2. **`-` 만 클램프가 있다.** `+`·`x`·`/` 에는 하한이 없다.
3. `fixed`·`silbiLimit` 의 `fixedAmount` 가 `null` 이면 **금액 유지**(0 이 아니다) —
   `calc-condition-engine.test.ts:148`(fixed) · `:1024-1026`(silbiLimit).

### 2-2. `normalizeOperator` — 대문자 백엔드 enum 별칭

`calc-condition-engine.ts:39-51`.

| 입력(백엔드) | 정규형 |
|-------------|--------|
| `NONE` | `none` |
| `FIXED` | `fixed` |
| `UNPAID` | `unpaid` |
| `ADD` | `+` |
| `SUBTRACT` | `-` |
| `MULTIPLY` | `x` |
| `DIVIDE` | `/` |
| `null` · `undefined` · `''` (falsy) | `none` (`:40`) |
| 그 외 매핑에 없는 값 | **원문 그대로 반환** (`:50`) → `applyOperator` 의 `default` 분기 → 금액 무변경 |

> **⚠️ `SILBI_LIMIT` 별칭이 없다.** 매핑표에 `silbiLimit` 에 대응하는 UPPER_SNAKE 항목이 없어,
> 백엔드가 `SILBI_LIMIT` 로 내려주면 원문 그대로 통과해 `default` 로 떨어지고 **금액이 무변경으로 바뀐다.**
> 관리자 저장값이 소문자 `silbiLimit` 이므로(§2-1) 현행 경로에서는 문제가 되지 않는다.
> 외부 시스템은 **응답에 실린 문자열을 그대로** 위 표에 대입할 것 — 자기 쪽에서 대문자화하지 말 것.

### 2-3. `PERCENT_UNITS` — `operatorUnit` 의 퍼센트 해석

`PERCENT_UNITS = ['PERCENT', '%']` (`calc-condition-engine.ts:36`).

```text
isPercent ← (cond.operatorUnit != null) AND (cond.operatorUnit ∈ ['PERCENT', '%'])    # :134
```

| 조건 | 해석 |
|------|------|
| `operator='x'`, `operatorUnit='PERCENT'`(또는 `'%'`) | `operatorValue` 는 **퍼센트** → `amount × (v/100)` |
| `operator='x'`, `operatorUnit='AMOUNT'` | `operatorValue` 는 **배수** → `amount × v` |
| `operator='x'`, `operatorUnit=null` | 퍼센트 **아님** 으로 취급 → 배수 (`:133` 주석) |
| `operator` 가 `x` 가 아닌 경우 | **`operatorUnit` 을 아예 읽지 않는다** |

`operatorUnit` 의 값 집합은 `PERCENT` · `AMOUNT` 다 (`renewal-limit-api.ts:230`,
백엔드 `CalcConditionSaveRequest.java:58` 「연산 단위: PERCENT, AMOUNT」).

검증 (`calc-condition-engine.test.ts:152-159` · `operatorUnit=null` 은 `:462-475`):

| 입력 | 결과 (base 50,000) |
|------|------------------|
| `x` / `2` / `AMOUNT` | 100,000 |
| `x` / `70` / `PERCENT` | 35,000 |
| `x` / `2` / `null` | 100,000 |
| `+` / `10000` / `PERCENT` | **60,000** — `+` 는 `operatorUnit` 을 무시한다 |

### 2-4. `parseValue` — 문자열 → 실수

`calc-condition-engine.ts:53-57`.

```text
FUNCTION parseValue(value) -> number
  IF value == null:  RETURN 0            // null · undefined
  num ← parseFloat(value)                // 선행 숫자만 파싱 (JS Number.parseFloat 의미)
  RETURN isNaN(num) ? 0 : num            // 파싱 실패 → 0
```

- `''` → `parseFloat('')` = NaN → **0**
- 결과적으로 `operatorValue` 가 비면 `+`·`-` 는 무변경, `x` 는 `×0`, `/` 는 0 나눗셈이라 무변경.
- **`parseValue` 는 `dailyDiff` 의 비율에는 쓰이지 않는다** (§4-2 — 그쪽은 NaN 을 0 이 아니라 "base 유지"로 처리한다).

## 3. `dayType` 필터와 적용 일자 커버 판정

`isApplicableOnDay` 는 세 가드의 AND 다 (`calc-condition-engine.ts:167-178`).
셋 중 하나라도 false 면 **그 날 그 조건을 건너뛴다**(금액은 이전 상태 유지 — 0 이 되지 않는다).
이것이 §1-2 의 `isDayCovered` 와 다른 점이다.

### 3-1. `isDayTypeMatched` — 요일 유형

`calc-condition-guards.ts:29-41`.

```text
FUNCTION isDayTypeMatched(cond, dayType) -> boolean       // dayType = response.dayTypeMap[date]
  FOR item IN (cond.items ?? []):                                                     # :34
      IF item.itemType NOT IN ['DAY_TYPE', 'dayType']:  CONTINUE                      # :20-22, :35
      value ← item.itemValue
      IF value is falsy OR value == '평일/공휴일':       CONTINUE   // 제약 없음        # :37
      IF dayType !== value:  RETURN FALSE                // 누락(undefined) 포함       # :38
  RETURN TRUE                                            // dayType 항목 없으면 항상 true
```

**값 집합**

| 축 | 값 | 근거 |
|----|----|------|
| 응답 `dayTypeMap[date]` (백엔드가 판정) | `평일` · `주말` · `공휴일` | `BstrRenewalLimitService.java:216-231` (`buildDayTypeMap`) |
| 조건의 `itemValue` (관리자 선택) | `평일/공휴일` · `평일` · `공휴일` · `주말` | `bstr-expense-rule/constants/calc-constants.ts:18` |
| 와일드카드(제약 없음) | `평일/공휴일` , 빈 문자열 | `calc-condition-guards.ts:17`(`DAY_TYPE_ALWAYS`), `:37` |

- 매칭은 **문자열 동등 비교**다. 부분 일치·집합 포함이 아니다.
- `itemType` 은 `DAY_TYPE`(대문자)와 `dayType`(camelCase) 둘 다 허용 (`:20-22`).
- `dayTypeMap` 에 그 날짜가 없으면(`undefined`) 구체값 조건은 **불일치**로 처리된다(`:38` 주석).
- 백엔드는 **공휴일 > 주말 > 평일** 순으로 하나만 배정한다(`buildDayTypeMap`). 즉 주말이면서 공휴일인 날은 `공휴일` 이며, `주말` 조건은 그 날에 걸리지 않는다.

검증 (`calc-condition-engine.test.ts:342-345`): 평일조건+평일=적용 / 평일조건+공휴일=스킵 / 주말조건+주말=적용 / `평일/공휴일`조건+주말=적용.

### 3-2. `isDateInRange` — 날짜옵션(`details.dateRange`)

`calc-condition-guards.ts:52-60`.

```text
FUNCTION isDateInRange(cond, date) -> boolean
  range ← cond.details?.dateRange
  IF range is null/undefined:  RETURN TRUE          // 제약 없음                       # :54
  from ← range.from || null   ;  to ← range.to || null    // '' 는 null 로 흡수         # :55-56
  IF from AND date < from:  RETURN FALSE                                              # :57
  IF to   AND date > to:    RETURN FALSE                                              # :58
  RETURN TRUE
```

- `date` · `from` · `to` 는 모두 `"YYYY-MM-DD"` → **문자열 비교로 안전**(타임존 무관, `:48` 주석).
- 한쪽만 있으면 그쪽 경계만 적용.
- 범위 밖 날짜는 그 조건만 건너뛰고 **기준금액을 유지**한다.

검증 (`calc-condition-engine.test.ts:367-370`): 조건 `7/1~7/31` + `+10,000`, 출장 `7/30~8/1`
→ `[50000, 50000, 40000]`.

### 3-3. `isPeriodDayCovered` — 기간옵션(`details.periodRange`)

`calc-condition-guards.ts:71-82`.

```text
FUNCTION isPeriodDayCovered(cond, dayNum) -> boolean     // dayNum: 1-based 일차
  pr ← cond.details?.periodRange
  IF pr is null/undefined OR pr.value is falsy:  RETURN TRUE                          # :73
  value ← Number(pr.value)
  IF NOT isFinite(value):  RETURN TRUE                                                # :75
  SWITCH pr.op:
      'gt'  -> RETURN dayNum >  value                                                  # :77
      'lte' -> RETURN dayNum <= value                                                  # :78
      'lt'  -> RETURN dayNum <  value                                                  # :79
      default (= 'gte' 및 미지정) -> RETURN dayNum >= value                            # :80
```

**`dayNum` 의 축이 함정이다** — `dayNum = index + 1` 로 **`limitAmounts` 맵의 정렬 인덱스** 기준이며,
요청 기간(`calcPeriod`)의 절대 날짜 기준이 **아니다** (`calc-condition-engine.ts:408-410`).
이유: 백엔드가 지급옵션(`applyPayOptionDays`)으로 맵에서 날짜를 먼저 제거하고,
백엔드의 `tripDays`(= `limitAmounts.size()`, `BstrRenewalLimitService.java:135`) 도 그 잘린 맵 기준이다.
프론트만 절대 축으로 바꾸면 FE/BE 매칭이 갈라진다 (`calc-day-position.ts:16-20`).

#### ★ 백엔드 `matched` 와 프론트 적용의 비대칭 (반드시 재현할 것)

백엔드는 `matched` 를 **"조건이 적용될 일차가 하나라도 존재하는가"** 로만 판정하고,
**실제로 어느 날에 적용할지는 프론트가 정한다.**

`BstrRenewalLimitService.java:384-386` 주석이 정본이다 —
「per-day 적용 전환: 실제 일차별 적용은 프론트 엔진(isPeriodDayCovered)이 수행하고,
백엔드는 "조건이 적용될 일차가 하나라도 존재하는가"(=matched)만 판정한다.
예) 31일 이하(lte 31) + 40일 출장 → 첫날(1)이 31 이하라 matched → 프론트가 1~31일차에만 적용.」

백엔드 판정식(`BstrRenewalLimitService.java:387-393`):

| `op` | 백엔드 `matched` 조건 | 프론트가 실제 적용하는 일차 |
|------|----------------------|--------------------------|
| `gte` (기본) | `tripDays >= threshold` | `dayNum >= threshold` |
| `gt` | `tripDays > threshold` | `dayNum > threshold` |
| `lte` | `threshold >= 1` (첫날이 조건에 걸리면 참) | `dayNum <= threshold` |
| `lt` | `threshold > 1` | `dayNum < threshold` |

> **외부 시스템이 `matched=true` 를 "전 일자 적용"으로 읽으면 40일 출장에서 32~40일차까지 조건을 얹어 금액이 부풀어 오른다.**
> `matched` 는 "후보 자격"일 뿐이며, 일자 배정은 `periodRange`·`dateRange`·`dayType` 을 프론트 규칙으로 다시 판정해야 한다.

### 3-4. `calcMethod` — 금액 커버 판정 (`isDayCovered`)

### 3-5. `DayPosition` 과 `resolveDayPositions` — 일차 기반 커버의 재료

`DayPosition` (`calc-day-position.ts:33-43`):

| 필드 | 타입 | 의미 |
|------|------|------|
| `slot` | `'pre' \| 'core' \| 'post'` | 이동일/코어 배정 |
| `isFirst` | boolean | 코어 첫날 |
| `isLast` | boolean | 코어 마지막날 |
| `dayFromEnd` | number | 코어 종료일로부터 경과 일수 (0 = 종료일) |
| `coreTotalDays` | number | 코어 총 일수 (`excludeN` 의 분모) |

`resolveDayPositions(dates, preCount, postCount, period)` 는 **두 축 중 하나**로 계산한다 (`:52-62`).

**(A) 절대 축** — `period`(= `response.calcPeriod`)가 있고 `isAbsoluteAxisApplicable` 이 참일 때 (`:82-115`)

```text
전제(:77-80): isValidYmd(period.start) AND isValidYmd(period.end)
              AND 모든 date 가 유효 YMD AND period.start <= date <= period.end   // 맵 ⊆ 기간
rawCoreStart ← period.start + preCount 일                                             # :89
rawCoreEnd   ← period.end   − postCount 일                                            # :90
isTravelDayAssignable ← (preCount>0 OR postCount>0) AND diffDays(rawCoreStart, rawCoreEnd) >= 0   # :91
coreStart ← isTravelDayAssignable ? rawCoreStart : period.start                       # :93
coreEnd   ← isTravelDayAssignable ? rawCoreEnd   : period.end                         # :94
coreTotalDays ← diffDays(coreStart, coreEnd) + 1                                      # :95
FOR date:
    slot    ← date < coreStart ? 'pre' : date > coreEnd ? 'post' : 'core'             # :100-102
    isFirst ← slot=='pre' ? TRUE : slot=='post' ? FALSE : (date == coreStart)         # :104
    isLast  ← slot=='post' ? TRUE : slot=='pre' ? FALSE : (date == coreEnd)           # :105
    dayFromEnd ← diffDays(date, coreEnd)                                              # :110
```

**(B) 상대 축(폴백)** — `period` 가 없거나 전제 불충족 시 (`:117-148`)

```text
lastIndex ← len(dates) − 1
isTravelDayAssignable ← (preCount>0 OR postCount>0) AND (preCount + postCount <= lastIndex)   # :124
coreStart ← isTravelDayAssignable ? preCount           : 0                            # :125
coreEnd   ← isTravelDayAssignable ? lastIndex−postCount: lastIndex                    # :126
coreTotalDays ← coreEnd − coreStart + 1                                               # :127
FOR index, date:
    slot ← index < coreStart ? 'pre' : index > coreEnd ? 'post' : 'core'              # :132-134
    isFirst / isLast 는 코어 sub-range 인덱스 기준                                     # :137-138
    dayFromEnd ← coreEnd − index                                                      # :143
```

**왜 절대 축이 필요한가** (`calc-day-position.ts:4-9`): 백엔드 `applyPayOptionDays` 가
지급옵션(`EXCEPT_END` 등)에 따라 `limitAmounts` 에서 날짜를 **먼저 제거**한다.
엔진이 "남은 맵의 끝"을 도착일로 오인하면 같은 규칙(`excludeArrive` 등)을 한 번 더 적용해 지급일수가 줄어든다.

골든 케이스 (`calc-condition-engine.test.ts:1032-1050`, TXR 2026-출장정산서-887):
기간 `08-05~08-12` · 맵 `08-05..08-11`(EXCEPT_END로 08-12 제거) · 조건 `excludeArrive`

| `calcPeriod` | 결과 |
|-------------|------|
| 있음 | 7일 전부 70,000 → **합 490,000** (08-11 은 절대 축에서 도착일이 아님) |
| 없음(폴백) | 08-11 이 도착일로 오인 → `0` → **합 420,000** |

**동치성**: 맵 == 기간인 응답에서는 두 축의 결과가 동일하다 (`calc-condition-engine.test.ts:1170-1189`).

> 외부 시스템은 `calcPeriod` 를 응답에서 받지 못한다 — 이 필드는 프론트가 요청의
> `bstrDate`~`bstrEndDate` 로 **스탬프하는 프론트 전용 필드**다
> (`renewal-limit-api.ts:368-374`, `:480`). 따라서 외부 시스템은 **자기 요청의 출장 시작/종료일을
> 그대로 절대 축으로 써야 한다.** 이것을 생략하고 맵 인덱스로 폴백하면 지급옵션이 적용된
> 응답에서 위 표의 오차(490,000 vs 420,000)가 그대로 발생한다.

## 4. `dailyDiff` 차등 적용 (첫날/중간/마지막)

`calcMethod` 가 `dailyDiff` 인 조건은 `applyOperator` 를 **타지 않는다** —
`calculateAmount` 가 `applyDailyDiff` 로 분기한다 (`calc-condition-engine.ts:157-159`).
**`operator` 는 무시된다** (`:60` 「dailyDiff: 첫날/중간/마지막 차등 적용 (operator 무시)」).
테스트가 이를 고정한다: `operator:'x'` 인 `dailyDiff` 조건이 `×` 가 아니라 비율로 계산된다
(`calc-condition-engine.test.ts:194-209`).

### 4-1. 모드 분기와 필드명

`details.diffType` 이 모드를 정한다 (`calc-condition-engine.ts:85`).
값 집합: `pct`(비율%) · `amt`(금액) — `bstr-expense-rule/constants/calc-constants.ts:253-256`.

| 모드 | `diffType` | 첫날 | 중간일 | 마지막날 | 기준금액 | 필드 위치 |
|------|-----------|------|--------|---------|---------|----------|
| 금액 | `'amt'` | `details.diffFirstAmt` | `details.diffMidAmt` | `details.diffLastAmt` | `details.diffBaseAmt` | `details` JSON (number, ± 허용) |
| 비율 | `'pct'` · 미설정 · 그 외 | `cond.diffFirst` | `cond.diffMid` | `cond.diffLast` | `details.diffBaseAmt` | 비율은 조건 **최상위**(string), 기준금액만 `details` |

타입 근거: `renewal-limit-api.ts:179-184`(`diffType`·`diffBaseAmt`·`diffCurrency`·`diffFirstAmt`·`diffMidAmt`·`diffLastAmt`) ·
`:233-235`(`diffFirst`·`diffMid`·`diffLast` — 최상위 string).

> **비율값은 `details` 가 아니라 조건 최상위에 있고, 금액값은 `details` 안에 있다.** 두 축의 필드명이 다르다(`diffFirst` vs `diffFirstAmt`).

### 4-2. `amt`(금액) 모드

`calc-condition-engine.ts:90-104`.

```text
diffAmt ← isFirst ? details.diffFirstAmt
                  : isLast ? details.diffLastAmt
                           : details.diffMidAmt                                       # :91-95
base    ← details.diffBaseAmt ?? amount        // 어드민 고정값 우선, 없으면 그날 기준금액   # :97
IF diffAmt == null OR NOT isFinite(diffAmt):
    RETURN max(0, base)                        // 가감 0 — base 는 그대로 유지          # :102
RETURN max(0, base + diffAmt)                                                         # :103
```

**기준금액 우선순위**: `details.diffBaseAmt` (어드민이 입력한 예외 기준금액) → 없으면(`null`/`undefined`) 그 날 base amount.
`diffBaseAmt` 는 `0` 도 유효한 설정값이다(`?? ` 는 `0` 을 통과시킨다).

**`max(0, …)` 절사**: 음수 결과는 0 으로 클램프.

**미설정 tier 규칙** (`:98-101` 주석): 해당 일자 가감액이 없으면 `max(0, base)` 를 반환한다.
`diffBaseAmt` 를 넣었으면 그 기준금액이 나오고, 안 넣었으면 그 날 규정 base 가 유지된다.
이 규칙이 없으면 "기준금액을 넣었는데 중간일만 규정금액이 나오는" 불일치가 생긴다.

검증 (`calc-condition-engine.test.ts`):

| 케이스 | 입력 | 결과 | 행 |
|--------|------|------|----|
| 음수 클램프 | base 40,000 · `diffMidAmt=-50000` | **0** | `:256-258` |
| 양수 가산 | base 40,000 · `diffFirstAmt=60000` | 100,000 | `:259-261` |
| tier 미설정 | base 40,000 · 가감액 없음 | 40,000 | `:268-270` |
| 비유한값 | `diffMidAmt=NaN` / `Infinity` | 40,000 (base 유지) | `:292-297` |
| 기준금액 우선 | base 40,000 · `diffBaseAmt=100000` · `diffFirstAmt=+5000` | **105,000** (규정 40,000 무시) | `:301-303` |
| 기준금액 + 음수 가감 | `diffBaseAmt=100000` · `diffLastAmt=-5000` | 95,000 | `:304-306` |
| `diffBaseAmt=0` + 미설정 tier | 규정 base 10,000 · `diffBaseAmt=0` | **0** (규정 10,000 아님) | `:314-316` |
| 레거시 비율값 혼입 | `diffType='amt'` + `diffMid='50'` + `diff*Amt` 없음 | 40,000 (비율 미적용) | `:287-289` |

### 4-3. `pct`(비율) 모드

`calc-condition-engine.ts:106-114`.

```text
rateStr ← isFirst ? cond.diffFirst : isLast ? cond.diffLast : cond.diffMid            # :107
IF rateStr is falsy:  RETURN amount            // '' · null · undefined → base 유지     # :108
rate ← parseFloat(rateStr)                     // ★ parseValue 아님                    # :110
IF isNaN(rate):       RETURN amount            // NaN → base 유지 (0 곱 아님)          # :111
base ← details.diffBaseAmt ?? amount                                                  # :113
RETURN base × (rate / 100)                                                            # :114
```

- **`parseValue`(NaN→0)를 쓰지 않는다.** 비율 빈값·NaN 은 `0` 이 아니라 **base 유지**다 (`:109` 주석).
  이유: `×0` 은 "미지급"이고 빈값은 "미입력"인데, 두 의미를 뭉개면 금액이 0 으로 사라진다.
- `rateStr = '0'` 은 truthy 문자열이므로 통과 → `rate=0` → 결과 0. (`''` 와 `'0'` 이 다르다.)
- **`max(0, …)` 클램프가 없다** — `amt` 모드와 다르다. 음수 비율을 넣으면 음수가 나온다.
- 결과는 실수 그대로다. `75 × 50% = 37.5` 가 그대로 나온다 (`calc-condition-engine.test.ts:747-778`).

**`pct` 의 base 가 그날 amount 가 아니라 `diffBaseAmt` 인 이유** — 소스 주석 (`:66-71`) 이 정본이다:

> 「기준금액 = details.diffBaseAmt(어드민 고정값). 없으면 그날 base amount(레거시 하위호환).
> pct + diffBaseAmt 조합은 누적 amount 와 무관한 고정 기준금액 사용.
> **규칙: pct base 가 그날 amount 가 아니라 diffBaseAmt 인 이유 — 차등 비율은 누적효과와
> 무관한 고정 기준금액에 대한 비율이다(수정사항 정의서 §4-1).**」

즉 `diffBaseAmt` 가 설정되면 **앞선 조건들의 누적 결과를 무시하고** 고정 기준금액에 비율을 건다.

검증:

| 케이스 | 입력 | 결과 | 행 |
|--------|------|------|----|

### 4-4. `isFirst` / `isLast` 우선순위와 1일 출장

3항 삼항식이 `isFirst` 를 먼저 본다 (`:91-95`, `:107`).
따라서 **`isFirst && isLast` (1일 출장 = 코어 1일)에서는 첫날 tier가 이긴다.**
검증: 1일 출장 · `diffFirst='70'`/`diffMid='50'`/`diffLast='30'` → **70** (`calc-condition-engine.test.ts:210-222`).

### 4-5. 다중 `dailyDiff` 조건과 제외일의 상호작용

`sortOrder` 순으로 순차 호출되므로 뒤 조건이 앞 조건 결과를 base 로 받는다(`:73-77` 주석).
제외일 조건(`excludeDepart`/`excludeArrive`/`excludeN`)으로 0 이 된 날도
**후속 `dailyDiff` 조건이 `amount=0` 을 base 로 갱신할 수 있다** — `sortOrder` 상 나중 조건이 우선한다.
소스가 이를 **의도된 동작(사용자 확정)** 으로 명시한다(`:74-77`). 제어하려면
`sortOrder` 를 제외 조건보다 낮게 두거나 조건을 분리한다.
단, `diffBaseAmt` 가 설정된 `dailyDiff` 는 누적을 무시하므로(§4-3) 이 상호작용에서 빠져나온다.

### 5-2. 어디서 어떻게 적용되는가

```text

    preConds  ← candidates where ∃ item : String(item.itemType) == predepartType
```

`hasItemType` (`:349-352`): `t` 가 falsy(`undefined`·`''`)면 **항상 false**.

|------|----------|----------|---------|---------------|

`pre` → `diffFirst`(또는 `diffFirstAmt`), `post` → `diffLast`(또는 `diffLastAmt`) (`:414`, `:419`).
검증: 익일도착 `dailyDiff` `100/100/50` → 마지막날 **37.5** (75×50%), `calc-condition-engine.test.ts:747-778`.
전일출발 `dailyDiff` `50/100/100` → 첫날 **37.5** (`:780-810`).

**배정 가드 (INNOTEK 실사고)** — 이동일 수가 일자 수를 잠식해 코어 범위가 비면
`isTravelDayAssignable = false` 가 되고 **전 일자를 코어로 되돌린다**(`calc-day-position.ts:91-94`, `:124-126`).
실측: 2일치 맵 + `pre/post=1` → `coreStart(1) > coreEnd(0)` → 두 날이 각각 전일출발·익일도착으로 오배정되어

회귀 게이트: `calc-condition-engine.test.ts:979-986`.
경계: 코어가 1일이라도 남으면 배정한다 (`:987-994`).

## 6. 외화 경로

### 6-1. 보류 판정 — `hasDeferredForeignCalc`

`renewal-limit-api.ts:416-423`.

```text
FUNCTION hasDeferredForeignCalc(response) -> boolean
  IF response.calcEnabled === false:  RETURN FALSE                                    # :417
  hasActiveCond ← ∃ cond ∈ (response.appliedConditions ?? []) : cond.matched AND NOT cond.overridden   # :418
  IF isForeignCurrencyCode(response.currencyCode):  RETURN hasActiveCond   // 케이스②  # :420
  RETURN collectDiffCurrencies(response).length > 0                          // 케이스①  # :422
```

| 케이스 | 조건 | 근거 |
|--------|------|------|
| **②** 외화 규정 | `currencyCode` 가 `null`·`''`·`'KRW'` 이 아님 **AND** `calcEnabled !== false` **AND** `matched && !overridden` 조건이 1개 이상 | `:412`, `:420` · `currency-utils.ts:19-22` |
| **①** KRW 규정 + 외화 조건값 | KRW 규정이라도 active 조건에 외화 `details.diffCurrency` 또는 외화 `fixedCurrency` 가 1개 이상 | `:413-414`, `:422` · `diff-currency-converter.ts:34-49` |

`collectDiffCurrencies` (`diff-currency-converter.ts:34-49`)는 active(`matched && !overridden`) 조건에서만
수집하며, `fixedCurrency` 는 `operator ∈ {fixed, silbiLimit}` 일 때만 본다
(`usesFixedAmountField`, `:26-29`).

> 여기서의 "active" 는 `matched && !overridden` 이다. 반면 **엔진의 대상 선정은 `matched` 만**이고
> `overridden` 은 일별로 판정한다(§1-1, §1-3). 두 기준이 다르다 — 혼동하지 말 것.

### 6-2. 소비 경로 — 일자별 환산 → `applyCalcConditionsKRW` 재적용

`applyCalcConditionsKRW(response, krwBaseMap, opts, labelOpts)` 는
`limitAmounts` 를 `krwBaseMap` 으로 **교체**한 뒤 같은 엔진을 돌린다 (`calc-condition-engine.ts:465-472`).
환산(외화→KRW)은 **호출자 책임**이다 — 경로별 환율 기준일이 다르기 때문이며, 이 함수는 **통화 무인식**이다(`:461`).

실제 순서 (`cloud-expense-report/utils/daily-cost-amount-utils.ts:321-418`, 주석 `:307-311`):

```text
1. 활성 계산식 유무 판정 — 없으면 null (스칼라 폴백)                                  # :338-355
2. diffCurrency/fixedCurrency 환율 조회 → applyDiffCurrencyToRule 로
   조건의 diff*Amt·diffBaseAmt·fixedAmount 를 KRW 로 환산한 rule 사본 생성            # :360-374
3. 규정 통화가 외화면 limitAmounts 를 일자별 exchangeToKRW 로 환산해 krwBaseMap 생성
   (환율 실패 시 null 폴백 — 통화 혼재 폭증 방지)                                     # :375-398
   KRW 면 krwBaseMap = { ...limitAmounts }                                            # :399-402
4. applyCalcConditionsKRW(convertedRule, krwBaseMap, opts)  ← 여기서 처음 조건 적용     # :404
5. eligibleDates 필터 후 일자별 Math.trunc 로 원 단위 버림 → 합산                      # :406-…
```

3축(`currencyCode` / `details.diffCurrency` / `fixedCurrency`)은 **서로 독립**이며 각자 통화로 조회해
이중환산이 없다 (`diff-currency-converter.ts:64-72`).

### 6-3. ★ 순서를 뒤집으면(조건 적용 → 환산) 안 되는 이유

> **이 절은 「금액 산출 경로」에 한한다.** 화면 산출내역 툴팁(`cloud-expense-report/utils/daily-cost-breakdown.ts:101-105`)은
> 외화 규정도 **환산 없이 원통화 base 위에** 조건만 적용한다 — 표기 전용이며 확정 사양이다.
> 그 코드만 보고 "환산을 안 해도 된다"고 읽으면 안 된다.

세 가지가 각각 독립적으로 결과를 깨뜨린다.

**(1) 엔진은 통화 무인식이다 — 서로 다른 통화가 한 식에 섞인다.**
`calc-condition-engine.ts:461` 「환산(외화→KRW)은 호출자 책임이다(경로별 환율 기준일이 다름). 이 함수는 통화 무인식.」
조건의 피연산자들은 규정 통화와 **독립인 자체 통화**를 갖는다 —
`details.diffCurrency`(차등금액), `fixedCurrency`(정액·실비제한)
(`diff-currency-converter.ts:3-5`, `renewal-limit-api.ts:232`, `:181`).
USD 기준금액에 KRW `fixedAmount` 를 `fixed` 로 대체하거나 KRW `diffFirstAmt` 를 더하면
**단위가 없는 숫자 연산**이 되어 값이 무의미해진다. 그래서 `applyDiffCurrencyToRule` 이
엔진 **진입 전에** 조건의 금액 필드까지 KRW 로 맞춘다(`diff-currency-converter.ts:5-6`).

**(2) `+`/`-` 의 `operatorValue` 에는 통화 필드가 아예 없다.**
`calc-condition-labels.ts:150-154` 「조건 스키마에는 `fixedCurrency`와 `details.diffCurrency`만 있고
`operatorValue`(±의 피연산자)에 대응하는 통화 필드가 **없다**.」
즉 `+10000` 이 10,000원인지 10,000달러인지 스키마상 결정할 수 없고, 표기조차 규정 통화를
엔진이 주입해 줘야 한다(`calc-condition-engine.ts:322-328`). 이 연산은 **KRW base 위에서만 정의된다.**
외화 base 위에서 먼저 더하면 그 값이 무슨 통화인지 사후에 알 수 없다.

**(3) 비선형 연산이 있어 환산과 교환법칙이 성립하지 않는다.**
`exchangeToKRW` 는 `Math.trunc` 로 원 단위 미만을 절삭하고 100단위 통화(JPY·IDR·VND)는 100 으로 나눈다
(`currency-utils.ts:11`, `:48-57`). 엔진 쪽에는 `max(0, …)` 클램프가 두 곳 있다
(`-`: `calc-condition-engine.ts:140`, `amt` 차등: `:102-103`).
`trunc` 와 `max(0,·)` 는 선형이 아니므로 `convert(f(x)) ≠ f(convert(x))` 다.
예: `-` 로 0 에 붙은 금액을 환산해도 0 이지만, 외화에서 음수로 내려간 뒤 환산하면 클램프 시점이 달라진다.
`Math.trunc` 도 소수 잔여를 어느 단계에서 버리는지에 따라 합계가 어긋난다
(`daily-cost-amount-utils.ts:406` 이후 주석: 「엔진 무반올림 → 일자별 원 단위 버림 후 합산」).

따라서 순서는 **환산 → 조건 적용 → (표시 단계에서) 일자별 `Math.trunc`** 로 고정이다.

검증 (`calc-condition-engine.test.ts:520-553`):

| 케이스 | 입력 | 결과 |
|--------|------|------|
| ADD | USD 100 원본 · `krwBaseMap=130000` · `+50000` | **180,000** (외화 원본 무시) |
| MULTIPLY(%) | `krwBaseMap=130000` · `×50%` | 65,000 (비율은 통화 중립) |
| 조건 없음 | `krwBaseMap=130000` | 130,000 (패스스루) |
| 이동일 `opts` 전달 | USD 75×1300 = 97,500 · pre 조건 `×50%` | 첫날 48,750 / 코어 97,500 (`:831-854`) |

| `label` | O | `buildLabel` (`calc-condition-labels.ts:172-177`) — 조건 항목 이름표를 `·` 로 연결. 항목 없으면 `'기본'` | `평일`, `국내출장·렌트카` |
| `effect` | O | `buildEffect` (`calc-effect-labels.ts:71-151`) — 연산 의미 1줄 | `+10,000원`, `변경없음`, `×50%`, `정액 50,000원`, `실비(제한) 16,500원`, `미지급(0원)`, `차등 100/50/100%`, `차등 +5,000원/0원/-5,000원, 기준 100,000원`, `익일도착일 50%` |
| `detailLabel` | 선택 | `detailLabelItems.join(', ')` | `전일출발 Yes, 합숙여부 No` |
| `detailLabelItems` | 선택 | `buildDetailedLabelItems` (`:214-221`) — 항목별 원소 배열 | `['출발시각 13:00 이상']` |
| `formula` | 선택 | `buildFormula` (`calc-formula-labels.ts`) — **지급기간 + 산출Value** | `출발일·종료일 지급. 정액 20,000 KRW`, `차등. 기준금액 30,000 KRW. 첫날 100% 중간일 50% 마지막날 100%` |

주의:

- `effect` 는 **연산 의미일 뿐 최종 금액이 아니다.** `-5,000원` 은 감산 연산을 뜻하며 엔진은 실제로 `max(0, amount − 5000)` 를 쓴다 (`calc-effect-labels.ts:11-12`).
- `detailLabel` 을 `', '` 로 다시 쪼개면 안 된다 — 이동수단 항목은 값 자체를 `', '` 로 잇는다(`렌트카, 택시`). 세로 배치는 `detailLabelItems` 를 쓴다 (`renewal-limit-api.ts:266-269`).
- `formula` 는 `effect` 와 **의도적으로 다른 표기**다. 지급기간을 앞에 붙이고, 이동일 전용 조건도 차등 3칸을 전부 보여준다(그래서 `travelDaySlot` 을 넘기지 않는다 — `calc-condition-labels.ts:245-247`).
- `effect` 는 반대로 이동일 슬롯이 정해지면 **실제 쓰이는 칸만** 표기한다(`차등 100/100/50%` → `익일도착일 50%`, `calc-effect-labels.ts:67-69`, `:87-98`).

### 7-2. `baseAmount` 는 `limitAmount` 가 아닐 수 있다

`resolveEffectiveBaseAmount` (`calc-condition-engine.ts:253-262`):

```text
effective ← fallback (= response.limitAmount ?? 0)
FOR cond IN active (sortOrder 오름차순):
    IF normalizeMethod(cond.calcMethod) != 'dailyDiff':  CONTINUE
    IF cond.details?.diffBaseAmt != null:  effective ← cond.details.diffBaseAmt   // 0 포함
RETURN effective
```

차등 조건이 예외 기준금액(`details.diffBaseAmt`)을 설정하면 엔진은 규정 base 를 무시하고 그 값으로 계산하므로(§4),
산출내역의 "기준금액"도 **실제 계산에 쓰인 값**으로 맞춘다. 여러 차등 조건이 각자 `diffBaseAmt` 를 가지면
`sortOrder` 상 **마지막 값**을 채택한다.

검증: `diffBaseAmt=100000` → `baseAmount = 100000` (규정 40,000 아님, `calc-condition-engine.test.ts:419-433`) /
미설정 → `baseAmount = 40000` (`:434-447`).

### 7-3. 조건 후보가 0건일 때

`matched` 조건이 하나도 없으면 `limitAmounts` 는 손대지 않고 `calcBreakdown` 만 만든다 —
`{ baseAmount: response.limitAmount ?? 0, items: [], totalAmount: sum(baseMap) }` (`calc-condition-engine.ts:335-340`).

## 8. 재현 체크리스트 (외부 시스템용)

> **구현한 뒤에는 `규정금액_골든벡터.json`(71건)으로 대조하십시오.** 이 절의 규칙을 문장으로
> 이해해도 어긋나는 지점이 있습니다 — 특히 `fixed`·`silbiLimit` 의 값 출처(`fixedAmount`),
> `calcMethod` 커버 실패의 의미(그 날 0), `dayTypeMap` 누락 시 범위, 이동일 배정 실패 시 되돌림.
> 벡터는 그룹별로 나뉘어 있어 **어느 규칙에서 갈렸는지** 바로 알 수 있습니다.


1. `calcEnabled === false` 또는 `appliedConditions` 없음 → **기준금액 그대로**.
2. `matched === true` 만 후보로 두고 `sortOrder` 오름차순 정렬. **`overridden` 으로 미리 걸러내지 말 것** (§1-3).
3. 일자 루프 안에서 조건 루프. 같은 날 안에서만 누적.
4. 매 조건마다 `dayType` · `dateRange` · `periodRange`(맵 인덱스 기준 `dayNum`) 3가드 → 통과 못 하면 **건너뛴다**.
5. `supersededByIds` 로 그 날 밀리는지 판정 → 밀리면 건너뛴다.
   **단 `supersededByIds` 가 없는 응답(구버전)에서는 `overridden === true` 를 전역 미적용으로 처리한다**
   (`calc-condition-engine.ts:189`). 두 경우를 갈라 구현하지 않으면 구버전 응답에서 밀린 조건까지 적용된다.
6. **이동일(전일출발·익일도착)이 있으면 조건을 3분할한다** — `preConds`(전일출발 항목을 가진 조건) ·
   `postConds`(익일도착) · `coreConds`(나머지)로 나누고(`calc-condition-engine.ts:371-379`),
   이동일 슬롯에는 그 슬롯의 조건만 적용한다. 이동일 슬롯에서는 `isFirst`/`isLast` 가 고정되고
   `isDayCovered` 판정을 생략한다(`:411-434`). **배정할 자리가 없으면 배정을 통째로 포기하고
   전 일자를 코어로 되돌린다** — 이 경우 pre/post 조건이 코어 조건으로 적용된다.
   opts 를 넘기지 않아도 같은 되돌림이 일어난다(조건이 사라지는 것이 아니다).
7. 코어일이면 `calcMethod` 커버 판정 → **커버 못 하면 그 날 금액을 0 으로**(건너뛰기 아님).
   `excludeN` 의 `excludeDays` 가 `null` 이면 `0` 으로 폴백해 **전 일자 커버**가 된다
   (`calc-day-position.ts:162`).
8. `dailyDiff` 면 §4, 그 외는 §2 의 `operator`.
9. **반올림하지 않는다.** 표시·검증 단계에서 일자별 `Math.trunc`.
10. 외화가 섞이면 §6 순서(환산 → 조건 적용)를 지킨다.
11. 계산을 **한 번만** 한다 (§1-4, §5-3).
12. `dayIndex`(일자 옵션) 조건이 오면 **전 일자에 적용한다** — 미구현 항목이라 백엔드가 무조건
    매칭 통과시키고 프론트에 가드가 없다(미확인 #3 참조). 일차 제한으로 해석하지 말 것.
