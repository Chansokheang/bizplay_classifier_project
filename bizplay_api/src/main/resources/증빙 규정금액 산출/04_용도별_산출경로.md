# §4 용도유형별 산출 경로 차이

> 같은 "규정금액(`ruledAmount`)"이라도 **용도유형(`tranKindType`)에 따라 산출 경로가 완전히 다르다.**
> 한도 조회 API(`POST /api/v2/bstr/policy/renewal/limit`)를 **몇 번 호출하는지**, 응답의 **어느 필드를 쓰는지**
> (`limitAmount` 스칼라 vs `limitAmounts` 일자별 맵), 그리고 **응답을 아예 쓰지 않는 예외**가 용도별로 갈린다.
>
> 이 절의 모든 단정에는 `파일:행` 근거를 달았다. 근거 파일의 루트는 `packages/domains/src/` 다.
> 확인되지 않은 것은 `⚠️미확인` 으로 표시하고 문서 끝 §4.13 에 모았다.

---

## 4.1 분기점 — 어디서 용도별로 갈리는가

정산서의 증빙 규정금액 재계산은 `updateReceiptsWithRuleInfo` 한 곳에서 용도별 모듈로 분기한다.

```
receipt.tranKindType === 'FOOD'  → updateFoodReceipt      (rule-update-food.ts)
receipt.tranKindType === 'ROOM'  → updateRoomReceipt      (rule-update-room.ts)
receipt.tranKindType === 'FUEL'  → updateFuelReceipt      (rule-update-fuel.ts)
그 외 전부                         → updateDefaultReceipt   (rule-update-default.ts)
```

근거: `bstr-policy/utils/rule-update-utils.ts:119-130`

전제 가드 — 아래 4개 중 하나라도 없으면 **재계산 자체를 건너뛰고 원본 영수증을 그대로 반환**한다
(`rule-update-utils.ts:107-109`).

| 컨텍스트 | 근거 |
|---|---|
| `bstrStartDate` · `bstrEndDate` (출장 기간) | `rule-update-utils.ts:107` |
| `bstrPurposeId` (출장 목적) | 같은 행 |
| `draftUserId` (기안자 = 한도 판정 사용자) | 같은 행 |

또한 증빙 1건의 재계산이 예외로 실패하면 **그 증빙만 원본 유지**하고 다른 증빙에는 영향이 없다
(`rule-update-utils.ts:117-134`). 외부 시스템이 이 계산을 직접 구현할 때도 같은 격리를 두는 것이
안전하다 — 한 건의 실패가 문서 전체 금액을 0으로 만들지 않게 한다.

> ⚠️ **분기 판정은 접두어 없는 값(`FOOD`/`ROOM`/`FUEL`)만 본다.** `HD_ROOM`·`HD_FOOD`·`HD_FUEL`
> 로 들어오면 전용 모듈이 아니라 **범용 경로(`updateDefaultReceipt`)로 떨어진다**
> (`rule-update-utils.ts:119-130` — `HD_` 를 정규화하는 호출이 이 함수 안에 없다).
> 일비만 두 형태를 모두 인정한다(§4.2 표 참조). → §4.13 미확인 ①

## 4.4 교통비 (`TRANSPORT`)

### (1) 범용 경로

`updateDefaultReceipt` 가 한도 조회 1회 → `resolveRuledAmount` 로 금액을 확정한다
(`rule-update-default.ts:120-146`, `:194`).

교통비 전용 요청 파라미터:

| 파라미터 | 값 | 근거 |
|---|---|---|
| `vehicleType` | `normalizeVehicleType(receipt.vehicleType)` — **교통비일 때만**, 다른 용도는 `null` | `:125` |
| `bstrRegionId` | 급지 ID. `findRegionIdForReceipt(bstrPeriodItem, receipt) ?? ctx.bstrRegionId ?? null` | `:104-105`, `:137` |
| `bstrDepartureId` | `getBstrDepartureId(ctx.bstrRoutes)` = **첫 경로의 `departureId`** | `:131`, `bstr-route-utils.ts:9-12` |
| `bstrDestinationId` | `getBstrDestinationId(ctx.bstrRoutes)` = **마지막 경로의 `arrivalId`** | `:132`, `bstr-route-utils.ts:15-18` |
| `totalDistance` | 유류비(`FUEL`)일 때만 전송, 교통비는 `undefined` | `:139-140` |
| `receiptEtcId` | 있으면 전송 — 백엔드가 왕복 티켓·터미널 정책금액 판정에 쓴다 | `:145` |

`vehicleType` 정규화 — `SRT`·`ITX`·`SAEMAEUL`·`MUGUNGHWA` 는 **`KTX` 규정을 공유**하므로 `KTX` 로
치환한다. 그 외 값은 그대로, 빈 값은 `null` (`bstr-policy/utils/vehicle-utils.ts:6-11`).

```ts
const KTX_EQUIVALENTS = ['SRT', 'ITX', 'SAEMAEUL', 'MUGUNGHWA'];
// → 'KTX'
```

> 교통비도 급지(`bstrRegionId`)를 전송한다. 레거시 구 규정 API(`/limit`)는 교통비를 급지 무관으로
> 조회했으나, **리뉴얼 규정(`/renewal/limit`)은 급지 기반으로 조회하므로 전송하지 않으면 규정이
> 매칭되지 않는다** (`rule-update-default.ts:134-136` 주석).

### (2) ★ 등급제(GRADE) 예외 — 규정금액 = 승인금액

**외부 시스템이 이것을 모르면 교통비 규정금액을 통째로 잘못 넣는다.**

```ts
// GAP-5: 교통비 GRADE 처리
if (tk === 'TRANSPORT' && rule.bstrCategoryType === 'GRADE') {
  return buildTransportGradeResult(receipt, rule);
}
```
`rule-update-default.ts:157-159`

`buildTransportGradeResult` 는 **한도 응답의 금액을 쓰지 않고 승인금액을 그대로 규정금액에 넣는다**:

| 세팅 | 값 | 근거 |
|---|---|---|
| `ruledAmount` | `receipt.approvalAmount ?? 0` | `rule-update-default.ts:67` |
| `calculateDefaultReqAmt` 의 `ruledAmount` 인자 | `receipt.approvalAmount ?? 0` | `:46` |
| `bstrCategoryType` | `rule.bstrCategoryType` | `:70` |
| `overseasRuledAmount` | 규정이 외화면 `rule.limitAmount`, 아니면 `null`. 영수증 통화 ≠ 규정 통화면 `null` 폴백 | `:59-63` |

신청금액 쪽에도 같은 예외가 있다 — `bstrCategoryType === 'GRADE'` 면 setting·외화 분기보다 **먼저**
승인금액을 즉시 반환한다 (`bstr-policy/utils/autofill-req-amount.ts:163-165`).

의미: **지급기준이 '등급'인 교통비는 "규정금액 = 실제 승인금액"이므로 초과가 발생하지 않는다.**
등급 제약은 금액 상한이 아니라 **좌석 등급 선택 제약**으로 걸린다(공공운임 API 기반 UI 분기 —
`business-plan/features/receipt-import/etc-receipt-drawer/EtcReceiptTransportFields.tsx:164-166`).

`bstrCategoryType` 값 3종: `MONEY`(금액) / `GRADE`(등급) / `STAR`(성급) —

### 숙박 일수 산정 — 체크아웃일 제외 (⚠️ 급지 분할 경로 전용)

> **이 제외는 모든 숙박 증빙에 걸리는 것이 아니다.** `usedEnd = usedEndDate − 1` 계산은 급지 루프
> 안(`:171-174`)에 있고, 그 앞 `:106-109` 이 `selections.length === 0` 에서
> `resolveRuledAmount(baseRule, receipt)` 로 **early return** 한다. 그 폴백은
> `usedStartDate ~ usedEndDate` 를 **포함** 합산한다(`rule-update-helpers.ts:197-208`, `−1` 이 없다).
> → **급지 selections 가 없는 숙박 증빙은 체크아웃일까지 합산된다.**

```ts
const usedStart = receipt.usedStartDate ? new Date(receipt.usedStartDate) : null;
const usedEnd = receipt.usedEndDate
  ? addDays(new Date(receipt.usedEndDate), -1)      // 체크아웃일 제외
  : (usedStart ? addDays(usedStart, -1) : null);    // 체크아웃 미입력 → 0박
```
`rule-update-room.ts:171-174`

| 상황 | 합산 구간 | 결과 |
|---|---|---|
| 1박 (`usedStart=D`, `usedEnd=D+1`) | `D ~ D` | 1일치 |
| 당일 (`usedStart = usedEnd = D`, 0박) | `D ~ D−1` (빈 구간) | **0원** |
| 체크아웃 미입력 | `D ~ D−1` (빈 구간) | **0원** |

> ⚠️ **이 제외는 지급옵션(`bstrPayOptionType`: `EXCEPT_END` 등)과 무관한 별개 축이다**
> (`rule-update-room.ts:160-170` 주석). 지급옵션은 규정 설정에 따라 백엔드
> `applyPayOptionDays` 가 `limitAmounts` 에서 날짜를 **미리 제거**해 내려주고, 체크아웃일 제외는
> **설정과 무관하게 증빙마다 항상** 적용된다. 겉보기가 같아("마지막 날을 뺀다") 한쪽을 다른 쪽의
> 중복으로 오인해 제거하면 **1박이 2일치로 계산되는 회귀**가 발생한다(실제 사례: 7만 → 14만).

### 급지별 합산의 3가지 경로

`rule-update-room.ts:183-263` — 급지별 응답마다 통화·계산식 상태에 따라 갈린다.

| B | KRW 규정이지만 조건식에 외화 `diffCurrency`/`fixedCurrency` 존재 | 환산 없이 `limitAmounts` 를 KRW base 로 쓰고, diff/fixed 금액만 환산해 엔진 재적용 | `:229-249` |

`currencyCode = null` 을 넘겨 **재환산(이중환산)을 막는다** (`:266-268`).

## 4.8 일비 (`DAILY_COST`) · 활동비 · 통행료

### (1) 일비 — 일별 규정금액 맵 + 조건 적용 보류

일비는 다른 용도와 달리 **fetch 시점에 조건식을 적용하지 않는다.**

```ts
function isDailyCostTranKind(response, requestTranKindType): boolean {
  const tranKindType = requestTranKindType ?? response.tranKindType;
  return tranKindType === 'DAILY_COST' || tranKindType === 'HD_DAILY_COST';
}
// applyValidatedCalcConditions
if (isDailyCostTranKind(response, requestTranKindType)) {
  const applied = applyCalcConditions(response);
  return { ...response, calcBreakdown: applied.calcBreakdown, calcDeferred: true };
}
```
`bstr-policy/api/renewal-limit-api.ts:434-440`, `:254-257`

| 필드 | fetch 직후 상태 | 근거 |
|---|---|---|
| `limitAmounts` | **원본(기준금액) 유지** — 조건 미적용 | `:251-256` |
| `calcBreakdown` | 산출근거만 채움(화면 툴팁용) | `:256` |
| `calcDeferred` | `true` | `:256`, 필드 설명 `:163-168` |

**이유** — 전일출발/익일도착 이동일 `opts` 가 **소비 시점**에 결정되므로, fetch 시점에 무-`opts` 로
적용해버리면 멱등 가드가 `opts` 재적용을 막아 **이동일 배정이 누락된다**(`:228-232`).

소비 시점(= 이동일 `opts` 를 아는 시점)에 딱 1회 적용한다.

| 소비 경로 | 무엇을 하는가 | 근거 |
|---|---|---|
| 정산서 — `resolveDailyCostRuledAmount` | 외화면 일자별 환산 → `applyCalcConditionsKRW(rule, base, opts)` → **`eligibleDates` 에 있는 날만** `Math.trunc` 후 합산 | `cloud-expense-report/utils/daily-cost-amount-utils.ts:321-418` |
| 계획서/검증 — `ruled-amount-calculator` path C | `calcBreakdown` 이 있어도 `calcDeferred === true` 면 `opts` 와 함께 1회 적용 | `bstr-policy/utils/ruled-amount-calculator.ts:107-119` |
| 규정 재계산 — `updateDefaultReceipt` KRW 분기 | `rule.calcDeferred` 면 `applyCalcConditionsKRW` 를 **여기서 1회** 적용 후 `resolveRuledAmount` | `rule-update-default.ts:191-193` |

`resolveDailyCostRuledAmount` 가 `null` 을 돌려주는(=스칼라 폴백) 조건 — `daily-cost-amount-utils.ts`:

| 조건 | 근거 |
|---|---|
| `limitAmounts` 없음/빈 맵 | `:333` |
| `rule.calcEnabled === false` | `:334` |

반대로 **활성 조건이 없어도 일별 맵을 합산해야 하는 두 경우**가 있다:

| 경우 | 왜 | 근거 |
|---|---|---|
| `payType === 'DIFF'`(차등지급) | 스칼라 `limitAmount` 가 0이고 첫날/마지막날 차등 금액이 `limitAmounts` 에만 있다. 스칼라 폴백은 `0 × 일수 = 0` | `:344`, `:61-64` 주석 |

### `convertRuledAmountToKRW(raw, currencyCode, receipt, ctx)` — 원화 환산

환율 기준일 컨텍스트는 `bstrStartDate`·`bstrEndDate`·`receipt.bldat`(승인일)·`receipt.usedStartDate`
4개를 넘겨 설정에 따라 고른다(`:50-58`).

> ### ★ 경고 — 환율 조회 실패 폴백은 초과금액을 **왜곡**한다 (방향은 통화에 따라 갈린다)
>
> `if (!exchangeRate) return { krwRuledAmount: rawRuledAmount, overseasRuledAmount: rawRuledAmount };`
> (`rule-update-helpers.ts:60-62`)
>
> 예: 규정 `USD 100`, 환율 조회 실패 → 규정금액이 **원화 100원**으로 채워진다. 초과금액은
> `MAX(0, 사용금액 − 규정금액)` 이므로 규정금액이 작아지는 방향이면 초과가 커지고, 반대로
> **왜곡 방향은 통화에 따라 반대가 된다** — 1단위의 원화 가치가 1원보다 **큰** 통화(USD·EUR·JPY 등)는
> 규정금액이 작아져 초과가 **과대** 표기되고, 1원보다 **작은** 통화(VND·IDR 등)는 규정금액이 커져
> **과소** 표기된다. `over-amount.ts:35-37` 의 경고는 후자를 전제로 쓰여 있어 무조건 성립하지 않는다:
>
> > ⚠️ 환율 조회 실패 시 `convertRuledAmountToKRW` 가 외화 원금을 원화 자리에 그대로 채우는
> > 선재 폴백이 있다(`rule-update-helpers.ts`). 그 경우 **초과금액이 과소 표기된다** —
> > 규정금액 컬럼도 같은 값을 쓰므로 이 함수만의 문제는 아니다.
>
> **외부 시스템이 규정금액을 직접 조립할 때는 환율 조회 실패를 "원금 그대로"로 넘기지 말고
> 오류로 다루는 편이 안전하다.** 급지·동행인 순회 경로(`ruled-amount-calculator.ts:63-66`)는
> 실제로 폴백 대신 `throw` 를 택했다 — "환율 없이 외화 금액을 원화처럼 합산하면 금액이 오염되므로,
> 묵시적 폴백 대신 throw 로 차단한다".

| `overseasRuled == null` 또는 `<= 0` | `null` (0/음수도 "외화 한도 미정의") | `:141` |
| 규정 통화가 없거나 `'KRW'` | `null` | `:142` |
| **영수증 통화 ≠ 규정 통화** | `null` → KRW 환산 경로 사용 | `:143` |
| 그 외 | `overseasRuled` 그대로 | `:144` |

왜 필요한가 — 규정이 `USD 100` 인데 영수증이 `JPY` 면, `overseasRuledAmount = 100` 을 그대로 두면
표기 시 영수증 통화와 합성되어 **"JPY 100"으로 잘못 표기**되고 외화 cap 비교에서도 다른 통화 금액을
직접 비교하는 오류가 난다(`:125-133`).

적용 지점: `rule-update-default.ts:200`, `:59-63`(GRADE), `rule-update-food.ts:120`,
`rule-update-room.ts:299`.

관련 판정 — `isCompareInForeign` 은 **영수증이 외화 + `overseasRuledAmount > 0`** 일 때만 외화 비교로
진입한다. 백엔드가 외화 규정 없는 증빙에 `null` 이 아닌 `0` 을 반환하므로 `0` 도 "불가"로 가드한다
(`foreign-currency-utils.ts:117-122`).

## 4.10 급지(지역등급) 순회 구조 — **여러 번 호출해야 한다**

정본: `bstr-policy/utils/ruled-amount-calculator.ts` (계획서와 정산서가 공유하는 단일 정본, `:1-11`).

> **외부 시스템이 "한 번만 호출하면 된다"고 가정하면, 급지가 섞인 출장에서 금액이 틀린다.**
> 급지가 바뀌면 매칭되는 규정 행이 바뀌고, 통화까지 다를 수 있다.

### 호출 횟수 = 급지 수 × 사용자 수

```
corpUserIds = (tranKindType === 'FOOD')
  ? [...활성 동행인 draftUserId, draftUserId]
  : [draftUserId]

for each 급지 selection (병렬)
  for each corpUserId (병렬)

```
`ruled-amount-calculator.ts:245-249`, `:281-302`

즉 **식비만 동행인 축으로 곱해지고**, 나머지 용도는 기안자 본인 한도만 조회한다(`:245-246` 주석).

### 급지 구간의 날짜 확장

```
첫 급지    : selectionName    − allowDays[0]
마지막 급지: selectionErpCode + allowDays[1]
중간 급지  : 확장 없음
```
`ruled-amount-calculator.ts:251-265`

`allowDays` 는 **용도별**로 `calculateAllowDays(issuedItems, tranKindId, null, fetchAllowBeyondDays)`
로 구한다(`:399-405`). `selectionName`·`selectionErpCode` 가 둘 다 없는 구간은 조회 대상에서 제외
(`:277-279`).

요청은 `buildLimitAmountsRequest` 가 조립하며(`:176-218`), 급지 축의 핵심은:

| 필드 | 값 | 근거 |
|---|---|---|
| `bstrRegionId` | `sel.selectionId ?? null` — **구간마다 다름** | `:198` |
| `bstrDate` | `sel.selectionName.slice(0, 10)` | `:195` |
| `bstrEndDate` | `sel.selectionErpCode.slice(0, 10)` | `:196` |
| `corporationUserId` | 사용자마다 다름 | `:186` |
| `vehicleType` | `TRANSPORT` 일 때만 `normalizeVehicleType`, 그 외 `null` | `:189-192` |

반면 **환율 조회 실패는 `throw`** 하여 그 급지 계산 전체를 중단한다(`:63-66`, `:126-130`) —
비대칭이 의도적이다.

### 급지별 부분 맵 → 일별 맵 합산

각 급지의 응답들을 `Record<YYYY-MM-DD, 원화>` 부분 맵으로 만들고(`buildSelectionPartial`, `:132-167`),
급지 내부에서는 **동행인별 금액을 같은 날짜에 `+=` 누적**한다(`mergeKrwAmountsIntoPartial`, `:99-119`).

`mergeKrwAmountsIntoPartial` 의 3경로(`:82-121`):

| 경로 | 조건 | 처리 |
|---|---|---|
| A | 외화 + `hasDeferredForeignCalc` | 일자별 `exchangeToKRW` → `applyCalcConditionsKRW(res, base, opts)` 후 누적 (`:92-101`) |
| B | 외화, 계산식 보류 없음 | 환산 후 그대로 누적 (총액 불변) (`:102-106`) |
| C | KRW | `calcBreakdown` 이 있고 `calcDeferred` 가 아니면 이미 적용됨 → 재적용 금지(멱등). 아니면 `applyCalcConditions(res, opts)` 를 **1회** 적용 후 누적 (`:107-119`) |

### ★ 급지 간 병합은 합산이 아니라 `Math.max` 다

```ts
for (const partial of perSelectionMaps) {
  for (const [dateKey, amount] of Object.entries(partial)) {
    dailyRules[dateKey] = Math.max(dailyRules[dateKey] ?? 0, amount);
  }
}
```
`ruled-amount-calculator.ts:325-329`

**이유** — 일비·숙박·식비는 "한 날짜당 단일 금액(per-diem)"이므로, 같은 날짜가 여러 구간(출장기간
행/급지)에 걸쳐도 **1회만 인정**한다. 서로 다른 날짜면 각자 1회(합산과 동일), 같은 날짜가 중복되면
최댓값으로 병합해 더블 카운트를 막는다(예: 출장기간 2행이 모두 `06-22` → `56,000 × 2 = 112,000`
더블 방지) (`:319-324` 주석).

**동행인 합산은 급지 내부(`buildSelectionPartial`)에서 이미 끝나 있으므로 이 `Math.max` 에 영향받지
않는다**(`:324`). 두 축을 뒤바꾸면 식비 동행인 한도가 사라진다.

### 환율 캐시

같은 통화·기준일의 환율 조회는 **용도 간 공유 캐시**로 1회만 수행한다(동행인·급지 중복까지 제거)
— `ruled-amount-calculator.ts:393-395`, `:240-242`. 진행 중 `Promise` 를 공유하므로 병렬이어도
동일 키 조회는 1회로 합쳐진다(`:274-276`).
