# §2 원자료 조회 계약 — 용도 한도 조회 API

> **이 절의 범위** — 규정금액(ruledAmount) 산출 3층 중 **① 원자료 조회**만 다룬다.
> ② 조건식 적용(프론트 계산)은 §3, ③ 검증은 §4 이후에서 다룬다.
>
> **가장 먼저 알아야 할 것** — 이 API 가 돌려주는 `limitAmounts` 는 **최종 규정금액이 아니라 기준금액**이다.
> 조건식(`appliedConditions`)을 적용해 최종 금액을 만드는 일은 **호출자(클라이언트)의 책임**이다. → [§2.5](#25--limitamounts-는-기준금액이다-핵심)

## 2.3  `calcInputs` 채우는 법

`CalcConditionInputs` (`renewal-limit-api.ts:103-149`) — **12 필드**.

### 2.3.1  `collectCalcInputs` 의 생략 규칙 (중요)

`collectCalcInputs` 는 **채워진 필드가 하나도 없으면 `undefined` 를 반환**하고, 호출자는 그대로 요청에 넣어
`calcInputs` 키 자체가 사라진다 (`calc-inputs.ts:33-34,82`).

| 조건 | 결과 |
|------|------|
| 시간·이동수단·목적지 어느 것도 없음 | `calcInputs` 미전송 → **기본금액 모드** |
| 하나 이상 있음 | 해당 필드만 담긴 객체 전송 |
| `calcInputs` 를 백엔드가 `null` 로 받음 | **빈 객체로 대체**되어 조건 매칭은 계속 진행된다 — 입력이 필요 없는 조건(`PURPOSE`·날짜 등)은 정상 매칭 (`BstrRenewalLimitService.java:85-89`) |

> 즉 `calcInputs` 를 아예 안 보내도 `calcEnabled` 규정에서는 조건이 매칭될 수 있다.
> 다만 입력이 필요한 조건(`YESNO_*`·`TRANSPORT`·시간·목적지)은 매칭되지 않는다.

### 2.3.2  `exceptionRuleInputItemIds` 수집 규칙

`collectExceptionRuleInputItemIds` (`calc-inputs.ts:189-205`) — **네 종류의 ID 가 하나의 배열에 합쳐진다** (중복 제거).

| # | 입력항목 `itemType` | 조건 | 담는 값 | 근거 |
|---|---------------------|------|---------|------|
| 1 | `BSTR_SELECT` | (조건 없음, 복수 항목 모두) | 선택된 옵션의 **`selection.selectionId`** | `calc-inputs.ts:190-193` |
| 2 | `EXPENSE_BEYOND_BSTR_PERIOD` | `value === 'true'` | **`item.id`** | `calc-inputs.ts:196-202` |
| 3 | `HOMETOWN` (본가/연고지·기숙사 신청) | `value === 'true'` | **`item.id`** | `calc-inputs.ts:196-202` |
| 4 | `REQUEST_STAFF_LODGE` (직원숙소 신청) | `value === 'true'` | **`item.id`** | `calc-inputs.ts:196-202` |

**주의** — 1번은 `selectionId`, 2~4번은 `item.id` 다. 서로 다른 축의 ID 가 한 배열에 섞인다.
체크 해제·`null`·다른 타입이면 제외되고, 그러면 백엔드 예외규정 매칭(`matchDynamicInputItem`)에서도 빠진다 (`calc-inputs.ts:187`).
백엔드는 이 배열을 `isItemMatched` 의 **`default` 분기**에서 소비한다 (`BstrRenewalLimitService.java:353`).

### 2.3.3  전일출발·익일도착의 두 갈래 경로

같은 사실("전일출발 체크됨")이 **두 경로**로 백엔드에 도달할 수 있다.

| 경로 | 필드 | 매칭 | 현행 클라이언트 |
|------|------|------|-----------------|
| A | `calcInputs.isFullDayDeparture` / `isNextDayArrival` | `YESNO_FULL_DAY_DEPARTURE` / `YESNO_NEXT_DAY_ARRIVAL` (`BstrRenewalLimitService.java:322-323`) | **사용하지 않음** |
| B | `exceptionRuleInputItemIds` 에 `EXPENSE_BEYOND_BSTR_PERIOD` 항목의 `item.id` | `matchDynamicInputItem` (default 분기, `BstrRenewalLimitService.java:353`) | **이 경로를 쓴다** (`calc-inputs.ts:196-204`) |

경로 A 는 입력이 없으면 조건이 **성립하지 않는다** — `matchYesNo` 는 `inputValue == null` 이면 `false` 를 반환한다
(`BstrRenewalLimitService.java:456-460`). 조건 값 문자열은 `"해당"` / `"미해당"` 이다 (`:458-459`).

한편 클라이언트는 같은 입력항목을 **이동일 계산(엔진 `opts`)** 용으로 한 번 더 읽는다:
`item.erpCode === 'PREDEPART'` → `pre=1`, `'NEXTARRIVE'` → `post=1` (`calc-inputs.ts:221-222,262-268`).
이 값은 §3 의 조건식 적용 단계에서 쓰이며 요청 페이로드에는 들어가지 않는다.

### 2.3.4  다중 급지 구간 — `applySelectionTime`

한 정산서에 출장기간 구간(급지)이 여러 개면, **구간별로 따로 조회**하면서 그 구간의 시각을 보낸다
(`calc-inputs.ts:94-104`, 사용 지점 `ruled-amount-calculator.ts:281-284`).

| 상황 | 동작 | 근거 |
|------|------|------|
| `bstrPeriodTimeUsed === false` | `baseInputs` 를 그대로 반환 (재지정 없음) | `calc-inputs.ts:99` |
| 해당 selection 에 출발·도착 시각이 모두 없음 | `baseInputs` 를 그대로 반환 (전역 폴백) | `calc-inputs.ts:102` |
| 시각이 하나 이상 있음 | `{...baseInputs, departureTime, arrivalTime}` — **두 값을 함께 덮어쓴다** (한쪽만 있으면 다른 쪽은 `null` 이 된다) | `calc-inputs.ts:100-103` |

`collectCalcInputs` 는 전역(첫 행 시작~마지막 행 끝) 시간을 만들지만, 구간별 조회는 그 구간의 체류시간으로
`timeCondition` 을 매칭해야 하므로 재지정이 필요하다 (`calc-inputs.ts:86-92`).

## 2.6  조회 직후 클라이언트가 하는 일 — 적용/보류 판정

`fetchRenewalLimitAmounts` (`renewal-limit-api.ts:466-485`) 는 응답을 받은 뒤 **네 단계**를 거친다.

```
[0] 요청 날짜 형식 검사        → 무효면 API 호출조차 하지 않고 null 반환   (:469-474)
[1] apiPost 로 조회                                                        (:476)
[2] calcPeriod 스탬프          → { start: bstrDate, end: bstrEndDate ?? bstrDate }  (:480)
[3] applyValidatedCalcConditions(response, request.tranKindType)           (:478-482)
```

### 3단계의 분기 — 즉시 적용 vs 보류

`applyValidatedCalcConditions` (`renewal-limit-api.ts:442-458`). **위에서부터 먼저 걸리는 것이 이긴다.**

| 순서 | 판정 | `limitAmounts` | `calcBreakdown` | `calcDeferred` | 근거 |
|------|------|----------------|-----------------|----------------|------|
| 1 | zod `safeParse` 실패 | **원본 유지** | 미세팅 | 미세팅 | `renewal-limit-api.ts:446-447` |
| 2 | `hasDeferredForeignCalc(response) === true` | **원본 유지(보류)** | 미세팅 | 미세팅 | `renewal-limit-api.ts:448-449` |
| 3 | 일비 용도 (`isDailyCostTranKind`) | **원본 유지(보류)** | **세팅** | **`true`** | `renewal-limit-api.ts:450-456` |
| 4 | 그 외 전부 | **조건 적용 후 값** | 세팅 | 미세팅 | `renewal-limit-api.ts:457` |

> 4번(즉시 적용)에서만 `limitAmounts` 가 최종 금액으로 바뀐다. 1~3번은 **기준금액이 그대로 남는다.**
> 응답만 보고 어느 쪽인지 알려면 `calcDeferred` (3번)와 `calcBreakdown` 유무를 본다.

### 보류 조건 3가지

| # | 조건 | 판정 코드 | 근거 |
|---|------|-----------|------|
| ① | **외화 규정 + active 조건 1개 이상** — `currencyCode` 가 외화(`KRW` 아니고 비어있지 않음)이고, `matched && !overridden` 조건이 하나 이상 | `isForeignCurrencyCode(response.currencyCode)` → `hasActiveCond` | `renewal-limit-api.ts:419-420` (`hasActiveCond` 는 `:418`), `currency-utils.ts:19-22` |
| ② | **KRW 규정인데 조건 쪽에 외화 통화** — active 조건의 `details.diffCurrency` 또는 (`operator` 가 정액 필드를 쓸 때) `fixedCurrency` 가 외화 | `collectDiffCurrencies(response).length > 0` | `renewal-limit-api.ts:421-422`, `diff-currency-converter.ts:35-49` |
| ③ | **일비 용도** — 요청/응답의 `tranKindType` 이 `'DAILY_COST'` 또는 `'HD_DAILY_COST'` | `isDailyCostTranKind(response, requestTranKindType)` | `renewal-limit-api.ts:434-439,453` |

**①② 를 무력화하는 선행 조건** — `response.calcEnabled === false` 면 `hasDeferredForeignCalc` 가 곧바로 `false` 다
(`renewal-limit-api.ts:417`). 즉 계산식을 쓰지 않는 규정은 외화여도 보류하지 않는다.

**①② 의 보류 이유** — 환율이 확정되는 소비 시점에 **일자별 환산 → 동일 엔진 재적용(`applyCalcConditionsKRW`)** 을
해야 하므로, 조회 시점에 `limitAmounts` 를 변형하면 안 된다 (`renewal-limit-api.ts:406-414`).
`applyCalcConditionsKRW` 는 소비 경로가 같은 import 경로에서 쓰도록 재노출된다 (`renewal-limit-api.ts:487-488`).

**③ 의 보류 이유** — 일비는 전일출발/익일도착 **이동일 `opts`** 가 소비 시점에 함께 적용되어야 한다.
조회 시점에 무-`opts` 로 적용해 `limitAmounts` 를 미리 변형하면 **멱등 가드가 `opts` 재적용을 막아 이동일 배정이
누락된다** (`renewal-limit-api.ts:426-432,450-452`). 그래서 화면 툴팁용 `calcBreakdown` 만 세팅하고
`limitAmounts` 는 raw 로 남긴 뒤 `calcDeferred: true` 로 표시한다 — 소비 경로는 이 표시를 보고
`opts` 와 함께 **1회만** 적용한다 (`renewal-limit-api.ts:362-366`).

`isDailyCostTranKind` 는 응답의 `tranKindType` 이 누락될 수 있으므로 **요청값을 우선(SoT)** 으로 쓴다
(`renewal-limit-api.ts:433,438`).

## 2.7  날짜가 무효하면 호출조차 하지 않고 `null`

외부 시스템이 반드시 알아야 할 **선행 가드**다 (`renewal-limit-api.ts:469-474`).

```typescript
  if (
    !isValidDateString(request.bstrDate) ||
    (request.bstrEndDate != null && !isValidDateString(request.bstrEndDate))
  ) {
    return Promise.resolve(null);
  }
```

| 항목 | 규칙 | 근거 |
|------|------|------|
| 검사 대상 | `bstrDate` (항상) · `bstrEndDate` (**`null`/`undefined` 가 아닐 때만**) | `renewal-limit-api.ts:470-471` |
| 형식 정규식 | `/^\d{4}-\d{2}-\d{2}$/` — **`YYYY-MM-DD` 고정폭** | `renewal-limit-api.ts:393` |
| 추가 검사 | `!isNaN(new Date(value).getTime())` — 실제로 파싱되는 날짜인지 | `renewal-limit-api.ts:394-396` |
| 위반 시 | **HTTP 요청을 보내지 않고** `Promise.resolve(null)` | `renewal-limit-api.ts:473` |
| ⚠️ enum 필드 위반 | `tranKindType`·`vehicleType`·`bstrType` 등 **enum 필드에 정의 밖 문자열**을 넣으면 역직렬화 단계에서 **400** 이다(`@JsonCreator` 가 없어 enum name 만 받는다). 값 집합은 [§2.2](#22--요청-필드-전수-표) 참조 | — |
| 응답이 falsy 일 때 | 조건 적용을 건너뛰고 응답을 그대로 반환 (`res ? … : res`) | `renewal-limit-api.ts:477,483` |

**⚠️ 와이어 형태 주의** — 백엔드가 규정을 못 찾아 `null` 을 돌려주는 경우, 컨트롤러가
`ResponseEntity.ok(result)` 로 감싸므로(`BstrPolicyRenewalController.java:48`) 실제 응답은
**HTTP 200 + 빈 본문**이다 — JSON `null` 문자열이 아니다. JSON 파서로 그대로 읽으면 파싱 실패나
빈 값이 되므로, **본문 길이 0 을 「규정 없음」으로 처리**해야 한다. 클라이언트는 falsy 를
`res ? … : res` 로 흡수한다.

**계약상 의미** — `null`(빈 본문)은 두 가지 서로 다른 사건을 같은 값으로 표현한다.

| `null` 의 의미 | 발생 지점 |
|----------------|-----------|
| ① 날짜 형식 위반 → **호출 안 함** | `renewal-limit-api.ts:469-474` |
| ② 규정 미존재 → 백엔드가 `null` 본문 반환 | `BstrRenewalLimitService.java:77-79` + `BstrPolicyRenewalController.java:48` |

> 클라이언트 소비 경로는 `rule=null` 을 **"규정 미조회"** 로 해석해 증빙을 **그대로 반환**한다
> (금액을 0 으로 깎지 않는다) — `rule-update-default.ts:148-154`.
> 즉 **날짜를 잘못 보내면 조용히 "규정 없음"으로 처리되고 규정금액이 채워지지 않는다.**
> 이것이 규정금액이 비는 대표 원인이므로, 외부 시스템은 `YYYY-MM-DD` 를 어기지 않아야 한다
> (`2026-9-8`·`2026/09/08`·ISO datetime 모두 위반).

또한 `tranKindType` 이 빈 문자열·`null` 이면 **백엔드가 400** 을 낸다 — 클라이언트는 그 앞에서 호출을 건너뛴다
